## 0. 问题陈述

当前项目（1036 款产品 / 40 品类 / 51 品牌）的数据工作流基于「四区流转协议」：
`_draft` → `_intake` → `_review` → `products.json`，靠 `scripts/flow.mjs` 驱动。

这套协议解决的是**「数据在哪个状态」**，没有解决**「多个人同时做不同的事时互不干扰」**。

随着数据量增长（缺口仍有 9392 个参数字段），工作模式必然转向多 Agent 并行。
本轮我尝试「一次回填 517 条竞品型号」时，架构的并发脆弱性集中暴露。

---

## 1. 实际触发的故障

### 故障 1：整文件覆写导致静默数据丢失（最严重）

**触发场景**：一次 publish 517 条，中途失败：

```
失败：UNKNOWN: unknown error, open 'D:\...\data\vacuum\products.json'
✓ vacuum/philips_1023678：修正区 → 已入库区（已替换库内同 id 条目）
✓ vacuum/philips_1092568：...
```

**根因**（`scripts/flow.mjs`）：

```js
function writeLibrary(file, data) {
  fs.writeFileSync(file, JSON.stringify(data) + '\n', 'utf8')   // :75
}
// publish 流程：
const lib = loadLibrary(key)      // 读整个 products.json 进内存
lib[idx] = product                // 改内存
writeLibrary(libFile_, lib)       // 整个文件覆写
```

**并发分析**：两个 Agent 同时 publish 同一品类时——
- Agent A 读 products.json（1036 条中的某版本）
- Agent B 也读同一版本
- A 改自己的条目 → 写
- B 改自己的条目 → 写，**A 的修改被完全覆盖，且没有任何报错**

这不是概率问题，只要两个 Agent 碰同一个品类就必然发生。**而且它静默**——
git 层面看不出异常（后一次 commit 包含完整文件），数据层面已经丢了。

**为什么现在的分区机制没挡住**：分区只隔离「未入库的数据」，**已入库的 `products.json` 没有任何互斥**。
而所有 Agent 最终都要 publish 到这里。

### 故障 2：`claim` 越权操作他人数据

**触发场景**：我 `flow:claim` 555 条 key，实际只应认领自己的 517 条。
结果把采集方 `collect-wash` 提交在 `_intake` 的 38 条也认领了。

**根因**（`scripts/flow.mjs` `cmdClaim`）：只按 key 查找文件并搬运，
**不校验这条数据是否由自己 submit**。`_intake/<品类>/<id>.json` 里没有 owner 字段。

**后果**：我把不属于自己的数据搬进了修正区。虽然最后我按 `change_log` 区分并只 publish 了自己的，
但这个隔离是**我在脚本里手工做的**，不是工具保证的。换一个 Agent 就可能真的覆盖掉别人的数据。

### 故障 3：批量操作无事务性

**触发场景**：`flow:submit <517 keys>` 中途出错。

**现状**：submit 是 `for` 循环逐条处理。第 300 条失败时：
- 前 299 条已进入 `_intake`
- 第 300 条及以后留在 `_draft`
- **没有任何批次记录**，我无法判断「这批到底提交成功了多少」

我最后的处理方式是重新扫描目录统计实际数量——这应该是工具提供的。

### 故障 4：分区半成品会被误提交

**触发场景**：我执行 `git add -A data` 想提交型号回填，
结果 `data/_intake/` 里采集方的 14 条、`data/_review/` 里 38 条**一并被暂存**。

**根因**：四个分区目录都在 `data/` 下，与库数据混在同一目录树。
`_draft` 里的数据按定义是「半成品，随意增删改」，把它 commit 进 git 意味着：
- 半成品被固化，别人 checkout 后看到的是不该看到的中间态
- 后续 `git checkout -- data/` 之类的操作会破坏别人的工作区

`.gitignore` 解决不了，因为**分区文件就是共享状态的一部分**（需要对方看见），
不能整体忽略。这个矛盾目前没有解。

### 故障 5：校验逻辑三处漂移

| 位置 | 内容 |
| --- | --- |
| `scripts/validate-data.mjs` | `npm run validate` 走这条 |
| `scripts/lib/product-check.mjs` | `checkProduct` / `checkSchema`，被 validate 调用 |
| `scripts/flow.mjs:504 validateCategory()` | **自己抄了一份**品类级循环 |

`flow.mjs` 的 `validateCategory` 与 `validate-data.mjs` 的品类循环逻辑相同但独立实现。
本轮我改 `validate-data.mjs`（适配两层 categories 结构）时，
**`flow.mjs` 也必须同步改**——如果我忘了，publish 的校验口径就会和 `npm run validate` 不一致，
出现「validate 通过但 publish 失败」或反之。

这类漂移在单人维护时靠记忆，在多 Agent 时是必然的 Bug 源。

## 2. 结构性分析

把上述故障抽象，架构有 6 个层面的缺口。

### 2.1 并发安全（缺失）

| 缺口 | 现状 | 后果 |
| --- | --- | --- |
| 库文件写入无互斥 | 整文件覆写 | 静默数据丢失（故障 1） |
| 无工作归属 | 文件存在 = 有人在改，不知道是谁 | 两个 B 同时改同一个文件（故障 2） |
| 批量操作无事务 | 逐条 for 循环 | 部分成功状态不明（故障 3） |
| 无锁过期机制 | 不存在 | Agent 中断后留下「永久占用」的假象 |

### 2.2 职责边界（混乱）

**核心矛盾**：`flow` 协议在做版本管理，`git` 也在做版本管理，两者职责重叠。

证据：
- `publish` 时记录 `supersedes: true`，并做「整品类复检 + 自动回滚」——
  这是在模拟 git 的「提交 + 冲突检测 + 回滚」
- 但真正的版本管理（谁改的、改了什么、能否回退）git 已经做得更好
- 结果：两套机制并存，`flow` 那套还是**更弱**的一版（无哈希校验、无法规回滚）

**更严重的**：`flow:publish` 的「整品类复检不过关就整体回滚」在并发下是错的——
A 的 publish 触发了品类复检，因为 B 的半成品数据不合规而失败，
A 的正确修改被回滚，且报错信息指向 B 的数据，**A 完全无法理解自己为什么失败**。

### 2.3 共享状态与工作区（混淆）

| 类型 | 应该 | 现状 |
| --- | --- | --- |
| 分区文件（`_draft`/`_intake`/`_review`） | **本机工作区**（草稿是私有的） | 在 git 里，被所有人 commit |
| 流转日志（`_flow/journal.jsonl`） | **共享事实**（append-only） | 在 git 里 ✓ |
| 已入库数据（`products.json`） | **共享事实** | 在 git 里 ✓ |

分区文件同时具有「私有工作区」和「共享交接物」两种属性，
当前用同一套机制（git）管理，必然出问题——这就是故障 4 的本质。

### 2.4 Schema 演进（无版本）

`schema.json` 是共享基础设施，A 可以直接改。问题：
- schema 变了，在途的 `_review` 数据按**旧 schema** 校验通过，publish 时按**新 schema** 可能失败
- 产品记录里没有 `schema_version`，无法判断某条数据是什么时候的 schema 下录入的
- schema 变更没有 review 环节

### 2.5 协调原语（缺失）

当前 Agent 之间**只能读文件和 journal**，没有：
- **锁**：看不出「空调品类正在被 X 修改」
- **议题**：数据疑点（「这个 CADR 两个来源冲突」）无处记录，只能等 review 时被发现
- **review 表达**：submit → publish 是流水线，但没有「我 review 了什么、通过/驳回」的记录载体
- **通信**：Agent 无法主动通知对方「我改了这个字段，你的脚本可能受影响」

### 2.6 性能（规模化后会显现）

`publish` 每条都跑 `validateCategory()`（遍历整个品类的所有产品）。
洗地机 47 款产品，publish 一条 = 校验 47 条。批量 517 条 = 上万次重复校验。
数据量再涨 10 倍这个开销会成为瓶颈。

## 3. 候选方案

以下方案**不互斥**，可组合。我按「改动成本 / 收益比」排序。

### 方案 A：乐观锁（最小改动，消除静默丢失）

**核心**：写入前校验内容指纹，冲突则拒绝。

```js
// flow.mjs publish
const before = hashFile(libFile_)          // 读之前记指纹
// ... 修改 ...
if (hashFile(libFile_) !== before) {       // 写之前再算一次
  console.error('库已被他人修改，请重新 load 后重试')
  process.exit(1)
}
writeLibrary(...)
```

**收益**：彻底消除故障 1。改动 < 30 行。
**局限**：只是**检测**冲突，不能**自动解决**。冲突时仍需人工介入。
**参照**：这正是 git 的 index.lock + 对象哈希做的事。

### 方案 B：文件级互斥锁（悲观锁）

**核心**：publish 时对 `data/<品类>/products.json` 加文件锁（`.lock` 文件或 `fs.open` 独占）。

**收益**：从根本上不产生冲突。
**局限**：
- 同一品类完全串行化，并行度降为 1
- Agent 崩溃会留下死锁，需要超时机制
- 跨 Agent 的锁（文件系统锁）在容器/远程环境下不一定可靠

**我的判断**：数据量再涨、品类数再多时，这个会成为瓶颈。**不建议作为主方案**，
可以作为方案 A 的补充（例如大批量 publish 时主动取锁）。

### 方案 C：git 分支 + PR（把版本管理还给 git）

**核心**：Agent 之间的合并冲突交给 git，flow 只管流程状态。

```
agent-a-data/    分支：采集方 A 的工作
agent-b-fix/     分支：修正方 B 的工作
main             分支：已发布数据
```

- 每个 Agent 在自己的分支上工作，`products.json` 的冲突由 `git merge` 检出
- `flow:publish` 变成「在自己的分支上 commit + 开 PR」，合入 main 才算上线
- 冲突解决有了标准流程（git 三方合并），不需要重新发明

**收益**：
- 版本管理、冲突检测、回滚、审计全部交给成熟工具
- `flow` 的「整品类复检 + 自动回滚」可以删掉（git 已经做了）
- 天然支持「一个 PR 涉及多条数据」的批量操作

**局限**：
- 需要 Agent 各自 clone 仓库、或用 worktree（当前是同一个工作区）
- Agent 需要能处理 git 冲突（`product-check.mjs` 的校验在 merge 后仍要跑）
- 引入分支管理的心智负担

**关键前提**：分区文件的归属问题必须先解决（见方案 D）——
否则分支上会带着别人的半成品。

### 方案 D：分区文件分层（解决工作区/共享的混淆）

**核心**：明确区分「私有工作区」与「共享交接物」。

| 位置 | 性质 | 是否入 git |
| --- | --- | --- |
| `data/_draft/` | **私有**（A 的半成品） | ❌ 进 `.gitignore` |
| `data/_intake/` | **共享**（交接队列） | ✓ 但只存「已完成的成品」 |
| `data/_review/` | **私有**（B 的工作台） | ❌ 进 `.gitignore` |
| `data/_flow/journal.jsonl` | **共享**（唯一事实源） | ✓ |
| `data/<品类>/products.json` | **共享** | ✓ |

**关键洞察**：`_draft` 和 `_review` 本质是**私有暂存**，
交接只需要「提交的那一刻」进入 `_intake`（共享）。这样：
- 私有区不进 git → 不会被误提交（解决故障 4）
- 共享区都是成品 → 冲突面小得多
- 交接信息通过 `_intake` 文件 + journal 传递

**局限**：
- 如果 A 和 B 在**不同机器**上工作，A 的 `_draft` B 看不见（这本来就是对的）
- 需要重新审视「待入库区是否要入库」——我认为要，它是交接物

### 方案 E：协调原语（补齐协作能力）

在 flow 之上加三个轻量原语：

```bash
# 软锁：声明「我在做这些」，别人能看到
flow:lock <品类/id>... --by <name> [--ttl 24h]
flow:unlock <品类/id>... --by <name>
flow:status --locks          # 谁在做什么

# 议题：数据疑点挂起，不阻塞其他工作
flow:issue new --cat air-conditioner --title "..." --detail "..."
flow:issue list [--status open]
flow:issue close <id> --by <name> --resolution "..."

# review 记录：谁 review 了什么
flow:review <品类/id>... --by <name> --verdict approve|reject --note "..."
```

**数据落地**：
```
data/_flow/locks/<品类>/<id>.json    { owner, acquired_at, ttl }
data/_flow/issues/<id>.json          { title, detail, status, author, replies[] }
```

**收益**：Agent 之间有了最小通信能力。
**局限**：这是「中心协调」思路，Agent 多了之后协调者本身会成为瓶颈。

### 方案 F：Schema 版本化（长期）

- `schema.json` 加 `version` 字段
- 产品记录加 `schema_version`（录入时的 schema 版本）
- schema 变更走独立流程，检测在途数据是否需要重校验
- 提供 `npm run schema:migrate <品类> --from v1 --to v2`

**收益**：schema 演进不再隐式影响在途数据。

## 4. 我的建议（供参考，非最终方案）

如果按「先止血、再建设」排序：

### 立即（1-2 天，零风险）

1. **方案 A 的乐观锁** —— 消除静默数据丢失，这是目前唯一会「悄悄丢数据」的问题
2. **`claim` 加 owner 校验** —— 只允许认领自己 submit 的（或显式 `--force` 并记录）
3. **分区目录的 git 策略明确化** —— 至少在文档里说清「`_draft`/`_review` 不要提交」，
   或用 `.gitignore` + 「交接时才入库」的约定

### 短期（1-2 周）

4. **方案 D 的分区分层** —— 私有区不进 git，从根上解决误提交
5. **批量操作加 `--batch`** —— 让「提交了 517 条，其中哪些成功」可查
6. **消除校验漂移** —— `flow.mjs` 删掉自己的 `validateCategory`，
   统一调 `product-check.mjs`（或反向：把品类级循环也抽到 lib 里）

### 中期（需先决策）

7. **是否引入 git 分支模型**（方案 C）—— 这取决于：
   - Agent 是否在同一工作区（现在是）
   - 是否接受 merge conflict 的人工介入
   - 分区私有化（方案 D）是否已完成
8. **协调原语**（方案 E）—— 取决于 Agent 数量。2-3 个时靠读 journal 就够，8+ 时需要锁与议题

## 5. 需要用户/第三方决策的问题

以下问题我没有把握，需要明确：

### Q1：Agent 是共享同一个工作区，还是各自 clone？

- **共享工作区**（现状）：git 分支模型不适用（分支会互相切），
  必须靠文件锁或乐观锁 + 严格的工作区纪律
- **各自 clone**：git 分支模型天然可用，但 Agent 需要处理 merge conflict
- **各自 worktree**（`git worktree add`）：两者兼得，但需要管理多个工作目录

### Q2：`_draft` / `_review` 应该是私有还是共享？

- **私有**（我的建议）：不进 git，通过 `_intake` 单向交接
- **共享**：保留现状，但接受「半成品被 commit」的风险

### Q3：多个修正方（B）同时改一个品类怎么办？

- **乐观锁**：检测到冲突就拒绝，让 B 重跑（简单，但 B 需要重做）
- **细粒度锁**：锁到产品级甚至字段级（复杂，但并行度最高）
- **品类级串行**：同品类同时只有一个人能改（简单但并行度低）

### Q4：schema 变更的审批权归谁？

当前 A 可以直接改 schema。schema 变更影响面最大（所有在途数据 + 全部前端渲染），
是否需要专门的 review？

### Q5：议题（issue）的粒度？

是「产品级」（这个产品有问题）还是「字段级」（这个产品的 CADR 有疑问）？
后者更精确但数据量大。

## 7. 结语

当前架构在**单 Agent 或低并发**下是清晰且够用的——
「四区流转 + 文件位置即状态」这个设计本身很好，它让协作状态可见、可查。

它的问题不在设计，而在**没有为「多方真正同时动手」准备**。
四区解决的是「同一件产品的状态流转」，没有解决「不同产品由不同人同时做」时的干扰。

最紧迫的只有一个：**`writeLibrary` 的整文件覆写会静默丢数据**（故障 1）。
其余问题可以慢慢演进，但这个问题每多一个并行 Agent 就多一分风险。

架构向（供参考）：

```
git         管「谁改了什么、能否合并、能否回退」——版本与冲突
flow       管「数据在哪个状态、谁负责推进」——流程与归属
locks      管「此刻谁在做什么」——互斥与并行
issues     管「有什么疑问待解」——异步协作
```

四者正交，各自做自己擅长的事，不互相模拟。
