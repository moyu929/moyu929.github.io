## 1. 背景与需求

- **用户需求**：支持**多个采集方与多个修正方同时工作**；数据可靠、协作不互相踩。
- **三个输入**：① 采集编排方的工作流意见（实战痛点、预判方案必败点）；② 审核修正方的
  并发架构诊断（五故障、六层缺口、候选方案 A–F）；③ 方案 v2 经**六轮评审往返**后定稿执行。
- 升级分四段：**P0 止血（10 项）→ P1 唯一写入规范（5 项）→ P2 协作切换（worktree/分支/PR/CI/锁）
  → P3 按需（写明触发条件）**。

## 2. 诊断：推翻直觉的关键事实

| 直觉 | 实测事实 |
| --- | --- |
| 「批量写库失败是并发引起的」 | 报错 `UNKNOWN: unknown error, open products.json` 发生在**无并发的单 Agent 批量写**（Windows 文件锁）——**批量稳定性比并发安全更前置**，故 P0-3/P0-4 先行 |
| 「claim `--by` 应等于提交人」 | 字面实现会**瘫痪所有正常 A→B 交接**（提交人 ≠ 认领人是常态）——改为 `selfReview` 警告 + journal 记 `submitActor` |
| 「B 是唯一写入者」 | 该约束在 **Python 侧不可达**——放宽为「**唯一写入规范**」（library-io 两侧实现） |
| 「lint 校验『型号应出现在产品名里』能防错」 | 规则**恒真**（`fill-model-codes.py` 的候选本就取产品名子串）——数学上不可能失败，撤除 |
| 「校验逻辑只有一份」 | 存在**三处校验漂移**（flow.mjs 自抄 validateCategory 等）——下沉 `lib/product-check.mjs` 统一 |
| 其他实证 | 42 个残留空目录（分区命令只删文件不删目录）；第 7 条写库路径 `extract-legacy.mjs`（死脚本）漏网 |

## 3. 落地内容

**P0 止血（10 项）**

| 项 | 内容 |
| --- | --- |
| P0-1 | 路径口径统一（5 个脚本 / 18 处裸相对路径 → `__file__`），**唯一有"根治"性质的越界防护** |
| P0-2 | 校验下沉：`lib/product-check.mjs` 的 `checkCategory()`，消灭三处漂移 |
| P0-3 | 库写入守卫：写前 sha256 指纹——不一致 `ELIBRARYCONFLICT` **立即失败、绝不重试**；`EPERM/EBUSY` 走有限退避重试。**两条路径严格分开**（共用会让守卫被重试架空） |
| P0-4 | 批量可审计 + 断点续跑：每批 batch id 入 journal；结束打印「成功/已是目标态/失败」；**原样重跑即幂等续上** |
| P0-5 | publish 回滚范围收窄 + 历史遗留问题分离（`--skip-legacy`，历史坏数据不再连累本批） |
| P0-6 | 归属可见化：`claim --from <提交人>` 批量认领、`selfReview` 警告、`flow:status --by` 过滤、未归类清单 |
| P0-7 | 操作自证：每条命令打印「数据根目录 + 分支 + actor」，journal 记 `branch` |
| P0-8 | 提交闸门：`commit-msg` 钩子随仓库走——含 `_intake`/`_review` 文件的提交必须带 `flow` 字样（挡"顺手 `git add -A`"） |
| P0-9/P0-10 | 工作区清理（死文件）；分区空目录清理（pruneEmptyDirs + 存量清除） |

**P1 唯一写入规范（5 项）**

| 项 | 内容 |
| --- | --- |
| P1-1 | `library-io.mjs` / `library_io.py`：规范序列化（一行一款、整值浮点归一、`ensure_ascii=False`）+ 指纹校验 + 文件锁重试 + **`actor` 留痕**（`batch-write`）；全部写库路径收敛到它 |
| P1-2 | products.json 转「一行一款」（40 品类 / 1036 款）——两分支改同品类时 git 能按行合并 |
| P1-3 | `.gitattributes`：`journal.jsonl merge=union`（两边各自追加合并时不冲突）；数据 JSON `eol=lf`（指纹基于字节，换行不能跟平台变） |
| P1-4 | `_draft/` 移出 git（私有工作台）；备份纪律：**能过校验就 `flow:submit`** |
| P1-5 | 图片回写目标**跟随产品所在分区**（不再无差别写 products.json） |

**P2 协作切换**：worktree + 分支 + PR + CI（PR 上跑 validate/lint/selftest/typecheck/build）+
`main` 分支保护；cutover issue #2 公告；首个 PR #3 完成「分支 → PR → CI → 合并 → 部署」全链路实战。

## 4. 关键分歧与裁决（六轮评审）

1. **lint「型号与产品名一致」规则**：经**三版反复最终撤除**——启发式 A 的 79 例命中全为小米系
   （营销名）、竞品 0 例；启发式 B 的 13 对全为合法后缀变体。撤除理由与三轮评审史写入
   `scripts/lint-data.mjs` 注释，防止将来"重新发明"。
2. **`model_code_source` 字段方案**：**两次否决**——第一次因规则恒真（见 §2），第二次因"12 款
   竞品来源不明"是 grep 口径错误（逐条查证 529 款竞品型号 100% 可溯源）。重新定位为
   「provenance 增强需求」，须另行论证。
3. **claim 语义**：按字面实现会瘫痪交接（见 §2）——`selfReview` 警告 + `--force` 记 `forced:true`。
4. **B 无法固定 cwd**：不追求硬隔离（做不到），改「**五条兜底**」——路径口径（唯一根治项）、
   指纹守卫、操作自证、提交钩子、编排方义务 + 会话纪律。态度 = **保证越界代价小且可见**。
5. **快照锁降级**：日常互斥由分区天然保证；快照锁只留「结构冻结 / 发版验收」，且冻结期间暂停流转。
6. **验收纪律升级**：「完成声明必须附验收输出，而不是声明」——乙评实测抓出两处
   「声称完成、实测未达成」（library_io.py 的 stdin 未按 UTF-8 重配导致 Windows 下乱码、
   空目录存量未清），此纪律成为全项目惯例。
7. **Python 侧细节**：`sys.stdin/stdout` 都要 `reconfigure(encoding='utf-8', newline='\n')`；
   指纹冲突与 EPERM 重试必须分流。
8. **`--from`/`--by` 至少一个非空**（否则 journal 记 `actor: unknown`，归属可见化在批量路径失效）。

## 5. 明确不做（及理由）

| 不做 | 理由 |
| --- | --- |
| 自研议题/看板 | GitHub Issues 免费且人类可直接参与 |
| `flow:lock` 软/硬锁 | 互斥场景只剩"同文件两进程同改"，由指纹守卫乐观处理 |
| `flow:status --all-worktrees` | **驳回**：跨 worktree 遍历会把「看不见彼此」这个已被 PR 解决的问题重新引入 |
| worktree 与 PR 分两期上线 | **驳回**：B 无法固定 cwd，worktree 先上会断掉传输链 |
| 立刻「每产品一文件」 | 一行一款已能按行合并；**触发条件见 §7** |
| schema 版本化（即时） | 先用「schema 变更随数据 PR 但单独 commit + CI 全库校验」兜住 |
| 自建 Agent 间消息通道 | PR/issue 评论区 + 会话开头清单已覆盖 |
| 删除 `flow.mjs` | 关口校验 + 跨区可见性是本站特有语义，git 不提供 |

## 6. 升级后的增量（2026-10-03 晚 ~ 10-04，P2 之后的真实运行）

- **在途清零**：52 款全部入库（1036 → 1088；actor 记 `third-party-upgrade` 便于溯源）。
- **P2 全链路落地**：协议 §3.6、分支保护（实测 `GH006` 拒管理员直推）、PR #3 合并后部署 34 秒成功。
- **多工作者并行（用户新需求）**：AGENTS §3.6「多工作者并行」——品类为分配单元（同品类至多 1A+1B）、
  共享文件串行、id 约定、**禁止共用工作目录**；`claim` 防双领占位（`<id>.json.claiming`，
  `wx` 原子创建）；每个工作者一个独立 worktree（`wt-collect-<NN>` / `wt-review-<NN>`）。
- **真实事故 → 规则**：两个会话共用主目录，一个切分支把另一个的未提交改动带走——
  由此确立「一人一个 worktree」；并新增 **`flow:workers`** 工作者视图（worktree 即天然注册表：
  路径=谁、分支=在做什么、未提交改动=活跃证据；读各工作台自己的 journal 做跨分支关联）。
- **合并代理**：用户授权编排方代理合并——常规批次（CI 全绿 + 描述完整）直接 `gh pr merge`；
  新增剔除 / 口径变更 / 冲突裁决先呈报用户；用户可随时叫停（PR #6/#4/#7/#8 已按此执行）。
- **数据裁决**：仅收录家用电器（剔除 33 款商用/工业机型，1088 → 1055，逐条依据记录在 journal）。
- **gh 环境修复**：凭据从「客户端会话注入」转存 **Windows 凭据管理器**——任何进程调用 gh 均可自动登录。
