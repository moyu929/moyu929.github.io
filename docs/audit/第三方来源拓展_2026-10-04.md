# 第三方来源拓展探测（2026-10-04）

## 结论先说

**找到了一个能补 `year` 的来源：苏宁易购。** 这是本轮唯一的实质性突破，其余平台全部堵死。

苏宁商品详情页的规格区带 **`上市时间（月）`** 字段（值如 `2024-10`），还有
`产品尺寸（宽*深*高）` 与 `国家能效等级`。关键在于它**可按型号批量定位**：
`https://search.suning.com/<型号>/` 的搜索结果页是**服务端渲染**的，一次 HTTP 请求
就能正则出 `product.suning.com/<vendorId>/<productCode>.html`，不需要 JS、不需要登录、
实测无验证码、无明显限流。

对站内 **year 缺口人群**（既有 `year` 空值、又有可用 `model_code` 的 555 款）实测 26 例：

| 环节 | 命中 | 命中率 |
| --- | --- | --- |
| 按型号搜到商品详情页 | 24 / 26 | **92%** |
| 详情页有 `上市时间` | 17 / 24 | **71%** |
| 详情页有尺寸 | 21 / 24 | **88%** |

外推到 555 款（按三步命中率连乘，保守估计）：

| 字段 | 算式 | 预计可补 |
| --- | --- | --- |
| `year` | 555 × 92% × 71% | **约 360 款** |
| `size` | 555 × 92% × 88% | **约 450 款** |

这是保守值：每款多试几个候选链接还能往上提，26 例的小样本本身也有 ±10% 的抽样误差。
但方向是确定的 —— 相比现状（`year` 888 全站零来源），这是第一个可执行的解法。

另外挖到两件事，详见后文：

1. **`probe-specs.py` 有假阴性 bug**，它把苏宁判成「只抽到 1 个规格字段」。已修复并验证。
2. **太平洋的「上市时间」字段已经被官方全站下架** —— 不是没取，是没有了。这解释了
   `year` 为什么一直零来源，也意味着这条路已经彻底封死，别再投人。

## 一、判据与方法

判据是**实测抽到的规格字段数 ≥ 5**，不是 HTTP 200。测的必须是**商品详情/参数页**。
早先的教训（科沃斯/添可/石头官方站 HTTP 200 但零字段，因为是 SPA）继续适用。

```bash
python scripts/probe-specs.py --url "<商品详情页URL>"
```

### 本轮修掉的一个假阴性（重要）

苏宁是本轮最有价值的来源，但 `scripts/probe-specs.py` 对它报的是：

```
✗ https://product.suning.com/0010342220/12440110157.html  连通但不可用：只抽到 1 个规格字段
```

**同一个 URL、同一份字节，换个提取器能抽到 42 个字段**，含 `上市时间（月）`。
原因是苏宁的参数区三种版式，原正则一个都匹配不上：

```html
<li><b>品牌</b>：海尔(Haier)</li>
<td class="name">…<span>产品尺寸</span></td><td class="val">830*594*1900毫米</td>
```

共同点是**键与值之间隔着闭合标签**，而原正则要求 `>键</th>` 这种「键自带闭合标签」。

已改 `scripts/probe-specs.py` 的 `parse_html_specs`：闭合标签类补上 `b|span`，
并新增两条苏宁版式路径。改完复测：

```
✓ https://product.suning.com/0010342220/12440110157.html  可用：抽到 9 个规格字段
    上市时间（月） = 2024-10
    国家能效等级  = 1级
    产品尺寸（宽*深*高）= 830x594x1900毫米
```

> ⚠️ **不改这个工具，下一个人会重蹈覆辙**：任何用现版工具复核苏宁的人，
> 都会得到「苏宁不可用」的结论，从而把唯一能补 `year` 的来源扔掉。

（附带：`http_fields` 会把导航栏文案也算进去（苏宁页面上 213），真正可信的信号是
`SPEC_WORDS` 命中数，即 `best_spec_hits`。）

## 三、`year`（888）—— 零来源字段的解法

### 现状复核

`year` 的 888 缺口其实是两种状态：

| 状态 | 数量 |
| --- | --- |
| `year: "查不到"`（已查过，明确没有） | 612 |
| 完全没有 `year` 键 | 276 |

**已查过 612 款**这件事很重要 —— 说明前几轮不是没努力，是在当时的来源下确实拿不到。

先排除两条便宜路（都实测过，是负结果）：

- **从产品名 / tags 派生年份**：888 款里名字含 `20XX年` 或 `XX款` 的有 **0 款**。此路不通。
- **GitHub 中文家电参数数据集**：不存在。`gh search repos "家电 参数 数据集"`、
  `"家电 爬虫"`、`"空调 参数"` 全部返回空或只有爬虫代码（且多为手机品类）；
  `gh search code "上市时间 型号 能效等级"` 0 结果。搜到的 `jd6979/JDScraper`
  （京东价格项目）里没有家电数据。**这条线可以彻底关闭，不要再查。**

### 为什么会零来源：太平洋有日期，但**只对 4 个品类开放**

太平洋规格表里有两个日期字段 `上市时间` 与 `发布时间`（版式是
`<th>上市时间</th><td>2024年,12月</td>`），**现在仍然在线**。
`data/_cache/pconline-*.json` 里 583 份历史缓存有 61 份带日期，
2026-10-04 又抽 30 个线上页面复核，**4/30 仍能抽到**（格力空调 `2024年,12月`、
索尼电视 `2025年,4月15日`、追觅与云鲸扫地机 `2024年`）。

> ⚠️ **本报告第一版在这里写错过，纠正如下**：最初复核时我用 `curl`（不带 `--compressed`）
> 抓 pconline 页面，服务器回的 gzip 二进制被当 UTF-8/gb18030 解码成乱码，
> 于是数出「上市时间 计数 0」，一度误判成「字段已被全站下架」。
> 加 `--compressed` 后字段照常在。**结论不是下架，而是品类门槛。**

真实情况是**按品类开放**，覆盖极不均匀：

| pconline 品类 | 带日期 / 缓存 | 占比 |
| --- | --- | --- |
| 电视 lcd_tv | 18 / 25 | 72% |
| 扫地机 sweepingrobot | 24 / 36 | 67% |
| 空调 air_condition | 16 / 30 | 53% |
| 洗衣机 washer | 3 / 30 | 10% |
| **其余 25 个品类** | **0** | **0%** |

**所以 `year` 零来源的真实原因不是「没有来源」，是「来源只覆盖 4 个品类」。**
按各品类缺口与上述覆盖率估，太平洋最多能再贡献约 **75 款**
（空调 44×53% + 电视 31×72% + 扫地机 37×67% + 洗衣机 56×10%）；
剩下 800 多款（厨电、冰箱、净水、清洁、小家电）在太平洋这条路上**确定拿不到**。
苏宁正好补的就是这一块，两者互补而非重叠。

顺带一个白捡的：**27 款**产品的 `year` 现在还是「查不到」，但它们的 pconline 缓存里
就有日期，零抓取成本可直接回填（映射脚本见 `data/_cache/probe-pconline-date-map.json`）。

> ⚠️ 这 27 款回填前仍须按 `SKILL.md` 纪律核对型号 —— 太平洋本身就有系统性错标
> （水箱单位错、型号栏塞产品名），缓存里的型号与站内产品型号必须逐项比对后才敢采。
> 缓存里的日期是历史旧值，与苏宁的时间轴未必一致，两边冲突时以苏宁为准。

### 正解：苏宁的 `上市时间（月）`

**字段形态**（实测样本）：

```
上市时间（月）  2025-01 / 2024-09 / 2026-07 / 2020年11月 / 2026-08-17
```

**批量取法**：

1. `GET https://search.suning.com/<URL编码型号>/`
2. 从服务端 HTML 正则出 `product\.suning\.com/(\d+)/(\d+)\.html`
3. `GET https://product.suning.com/<vendorId>/<productCode>.html`
4. 抽 `上市时间（月）`

三步全是纯 HTTP，无浏览器、无登录、无验证码。

**限流实测**：连续 12 次请求（无间隔）全部 200，响应字节完全一致，总耗时 2.9 秒
（单次 0.19–0.29 秒）。按 555 款 × 2 请求算 ≈ 1110 次请求，串行约 4.5 分钟，
不需要退避重试。

**为什么这条对缺口人群有效**：888 款里有 **555 款带可用 `model_code`**（543 款只有
model_code，12 款 model_code + miot_model 都有）—— 这 555 款可以直接按型号搜。
剩下 333 款只有 `miot_model` 或什么都没有，得改用中文产品名搜（苏宁也接受中文名，
但命中率需另测）。

#### 三个必须写进规范的风险

1. **搜索排名很松，必须逐条核对型号。** 实测搜 `MB-EFB4022H` 返回的是苏泊尔
   `SF50FC733`；搜 `XQG100-ABLEU70D1U1` 返回的是 `XQG130-ABLEU70D3U1`；
   搜 `BCD-560WGHTD1BWLU1` 只返回 507 系。**不能只看搜到了就采** ——
   这与 `SKILL.md` 里「只比对型号字符串会误判，必须逐项比对制冷量/容积/噪音」是同一条纪律。
2. **日期格式三种，且有日精度的疑似上架日。** 26 例里 15 例是 `YYYY-MM`（可信）、
   1 例 `YYYY年M月`、**2 例是 `YYYY-MM-DD`**。后两者里的 `2026-10-01`、`2026-08-17`
   距今天（2026-10-04）只有几天，**那明显是「上架日期」被塞进了「上市时间（月）」字段**，
   不是上市时间。日精度的值一律不采。
3. **同一 `productCode` 会挂在多个 `vendorId` 下**（实测 `12440110157` 同时出现在
   `0010342220` 和 `0070165541`，数据完全相同）。去重要按 `productCode`。

## 四、`size`（556）—— 苏宁同样能补

口径说明：`size` 现状是 **480 款有值 / 417 款「查不到」/ 139 款无键**，缺口合计 556。

苏宁详情页的尺寸字段**一个产品给三到四条**：

```
产品尺寸（宽*深*高）   830x594x1900毫米     ← 取这个
包装尺寸（宽*深*高）   892x656*2015毫米     ← 不要，是包装箱
预留尺寸(宽/深/高)    838 / 600 / 1909毫米
内机尺寸(宽×高×深）   450×1830×380毫米     ← 空调，取这个（注意轴序不同）
```

要点：

- 键名不统一（`产品尺寸（宽*深*高）` vs `内机尺寸(宽×高×深）`，全角半角括号混用），
  建议按「键含 `尺寸` + 值匹配 `\d+[*x×]\d+[*x×]\d+`」筛，不要硬编码键名。
- **单位脏**：实测出现 `596x600x845毫米毫米`（单位重复）与 `16`（根本不是尺寸，
  疑似取到了「加热管尺寸」）。必须过单位守卫与形状校验。
- 轴序不一致（宽*深*高 vs 宽×高×深），入库前要与现有 `size` 值比对确认轴序。
- 覆盖率：555 款有型号的缺口产品里实测 **88%** 带尺寸。

ZOL 参数页也带 `产品尺寸`（实测 `596*636*850mm`），可作第二印证 —— 但 ZOL 搜索
接口对本项目型号返回无关结果，只能靠品类页枚举，作为补充而非主力。

### 两个会让人「自信地答错」的坑

这两个不是死路，是**探测方法本身的陷阱**，比找不到来源更危险：

1. **太平洋旧 URL 会 302 到一个返回 HTTP 200 的 404 页。**
   `www.pconline.com.cn/product/...` 现在全部落到 `www1.pconline.com.cn/page/errors/404.html`，
   而那个页面**回 HTTP 200**。任何只看状态码的连通性检查，都会在一个已经死掉的 URL 上报「成功」。
   本轮一开始 `www.pconline.com.cn/product/` 就是这么被判成「连通」的。
   判据必须是**抽到的字段数**，不是状态码 —— 这也是 `probe-specs.py` 存在的理由。

2. **IT168 搜索结果前 3–4 条是恒定的页头「热门搜索」链接**，与查询词无关
   （`/detail/1151397.html` 小米Pro、`1155475.html` 尼康D850、`1162398.html` 惠普星14）。
   直接正则取前几条必然命中假结果。搜「海尔」和搜「美的」返回的还是**字节完全相同**的页面
   （都是 81061 字节、同样 48 条链接）—— 中文品牌词根本传不进它的搜索。
   同理，它的关键字必须是站内的 `$uXXXX$uXXXX` 编码（海尔 = `$u6d77$u5c14`，冰箱 = `$u51b0$u7bb1`）。

## 补充：`scripts/suning-lookup.py` 的型号门槛把命中率砍掉一半

本报告初版估算 `year` 命中率 71%，那是**按「搜到了详情页」算的**。实际实现时
加了型号精确匹配门槛（苏宁详情页的 `<span>型号</span>` 行），洗衣机 12 款样本上：

| 判定 | 命中 |
| --- | --- |
| 只看「搜到了详情页」 | 10 / 12（83%） |
| **加型号逐字相等校验** | **4 / 12（33%）** |

实测反例：搜 `XQG100-ABLEU70D1U1`（西门子），返回页面里目标型号出现 **0 次**，
而 `XQG130-ABLEU70D3U1` 出现 37 次 —— 搜索把另一台机器的详情页给了我们，
连同它的 `上市时间（月）=2025-12` 一起。

**所以上文的 71% / 88% 是上界，实际约 1/3。** 即便如此仍是目前唯一可执行的
`year` 来源（888 缺口里预计能补 ~150–200 款），但排期时要按三分之一算，不要按七成。

型号门槛的判定只做**归一后完全相等**，不做包含、不做前缀匹配 ——
`XQG100` 是 `XQG100-ABLEU70D1U1` 的前缀，包含式匹配会错配到整个产品族。
