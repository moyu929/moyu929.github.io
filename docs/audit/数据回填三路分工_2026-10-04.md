
2026-10-04 已把字段映射从 28 个扩到 80+ 个，并加了**单位守卫**
（空调的 `产品功率` 写「1.5匹」、净化器的 `产品容量` 写「4.5L」，数值上能骗过阈值，
只有单位拦得住）。数据落在 `data/_cache/brand-*.json`（2653 条，含 `参考价` 与 `上市时间`）。

### 小米：官方商城 API（主力）

```bash
python scripts/fill-mi-official.py --report          # 看哪些产品定位不到 product_id
python scripts/fill-mi-official.py --cat <品类> --dry
python scripts/fill-mi-official.py --cat <品类>      # 写入 data/_draft/<品类>/
```

接口：`https://api2.order.mi.com/product/view?product_id=<id>&version=2`，
**必须带 `-H "Referer: https://www.mi.com/"`**，否则返回 200 + 空 body（很容易误判成「商品不存在」）。

返回 `data.goods_list[0].goods_info`：
- `price`（现价）→ `official_price`，`market_price`（划线价）→ `ref_price`
  （两者相等时不写 `ref_price`，那不是促销价，只是重复）
- `class_parameters` → 商城「关键参数」，含 CADR、建议最大适用面积、能效等级、滤网类型等。
  只取 `is_page_show` 为真的条目。
- **带「（实测值）」的一律转 `_real` 列**，不与额定值混写（脚本已按此分流）。

`product_id` 两个来源：产品 `verify_url` 的 `product_id=`（167 款），
以及本地商城缓存 `data/_cache/search-*.json` / `product-*.json` 按名反查。
**251 款两者都拿不到** —— 这批要先用 `npm run mi:enumerate -- <关键词>` 重新枚举
（需要 Playwright），或从官网商品页人工取 id。这是小米侧的主要瓶颈。

### 卖点标签

`pros` / `cons` 由该产品已入库的参数 + 官方卖点文案（商城 API 的 `class_parameters` 与详情页营销语）推导。
不引入新数值，只描述已有参数，**不得出现参数表里没有的数字**。
827 款产品这两项同时为空（裸卡），是当前对观感影响最大的缺口。

## 硬约束（三方共同遵守）

1. **只写自己品类**。`data/<品类>/products.json` 与 `data/_draft/<品类>/` 互不重叠。
2. **不改 `categories.json` / `schema.json` / `_sources/**`**。需要改 schema 的诉求单独提 PR，不与数据批次混在一起（AGENTS.md §3.6）。
3. **写库必须走 `scripts/lib/library-io.mjs`（Node）或 `library_io.py`（Python）**，不自己 `writeFileSync`。批量工具要传 `actor`。
4. **每个品类一个 PR**，PR 描述写清品类、字段、来源、跳过条目及原因。
5. **不写 `second_hand`**。填不出来就保持「查不到」，不要用新机价折算。
6. **不猜**。数值必须能落到具体链接；只有一条媒体来源的不定值。
7. `data/_cache/` **不入库**（`.gitignore` 已排除）。每个 worktree 需自行准备缓存，缺失时按上面的命令重抓。

## 验收

每路完成后 `npm run check` 全绿（validate + lint + selftest + audit:check），并在 PR 里给出：

- 本批次回填字段数 / 仍为空数（按品类列表）
- 每条回填的来源类型分布
- 被阈值剔除、被判为存疑而跳过的条目清单及原因

`flow:status --unclassified` 的未归类清单在各自品类内一并处理完。
