## 2. 关于 lint 撤掉「型号/名称一致性」—— 结论对，理由需修正

开发方撤掉该规则，理由是「两种启发式实测均以误报为主」。**结论我同意，但理由不准确，且据此推广会丢掉一类真问题。**

### 2.1 启发式 A 的误报是**分层的**，不是全域的

我复现了「产品名应含 model_code」这条规则：

```
启发式A（名不含型号）: 79
  其中小米系: 79    竞品: 0
```

**79 例全部是小米系，竞品 0 例。** 开发方把它们合并统计成「误报为主」，但这掩盖了一个重要事实：

- **小米系误报是结构性的、且永远误报**：`米家空调 巨省电Pro 大1匹（超一级能效）` 配 `KFR-26GW-NA20/V1A1` ——
  国标型号天然不出现在营销名里，**这条规则对小米系永远无意义**
- **竞品 0 误报**：因为我这一轮给 529 款竞品回填的型号**全部来自产品名**
  （`fill-model-codes.py` 的逻辑就是从名称提取），所以竞品必然满足

**正确的做法不是全局禁用，而是按品牌分组**：规则只对 `brand !== 小米` 生效。

这样：
- 保留了对竞品的检查能力（未来竞品若型号不是从名称提取的，或手工填错，仍能发现）
- 完全消除 79 例小米系噪音

开发方提到「竞品也常见营销名（『TCL小蓝翼Q7Max新风 1.5匹』配型号 `KFR-35GW/…`）」——**这条我复现不出来**。当前 618 款竞品里，这种「营销名 + 国标型号」的组合 **0 例**（因为名字里就有 `KFR-`）。若将来出现，规则应升级为警告而非报错。

### 2.2 启发式 B 的 13 对里没有真问题

我复现了「同品类内型号互为前缀却不相等」，命中 13 对，逐对核对：

```
KFR-72LW/N8QM1P ⊃ KFR-72LW/N8QM1   （美的 2673219/2673299，两款不同机型）
KFR-72LW/E2-1Pro ⊃ KFR-72LW/E2-1   （海尔 2781199/2781259，两款不同机型）
MY-S5X28-Y4P  ⊃ MY-S5X28-Y4
ST-530ET      ⊃ ST-530
...
```

**全部是合法的不同机型**（后缀 P/Pro/S/ET 是厂家区分型号的方式）。开发方判断正确，这条规则噪音大于价值，我同意不做。

### 2.3 我的建议

**保留启发式 A，但限定 `brand !== '小米'` 且降级为「提示」而非「报错」**：

```js
// 只对竞品生效：小米系产品名是营销名（"米家空调 巨省电Pro 大1匹"），
// 国标型号（KFR-26GW-NA20/V1A1）本就不出现在名称里，对小米系检查必然全误报。
// 竞品不同：529 款回填的型号均来自产品名，此规则 0 误报，
// 能在「型号被手工填错 / 从非名称来源填入」时报警。
if (p.brand !== '小米' && !nameContainsCode(p.name, p.model_code)) → 提示
```

成本约 8 行，保留一类真问题的检查能力，同时不引入噪音。若将来出现竞品用营销名的情况，降级为提示即可，不会挡路。

**其余部分（重复型号检测、名称完全相同、标注覆盖率）我认为都该保留，现状正确。**

## 3. 我发现并已修复的两处缺陷

### 3.1 `library_io.py` stdin 编码缺陷 → `selftest` 未全绿

执行状态称「selftest 44/44 通过」，我实测是 **40/41**，唯一失败项：

```
UnicodeEncodeError: 'utf-8' codec can't encode character '\udcae' in position 23: surrogates not allowed
```

根因：`__main__` 只重配了 `sys.stdout`，**没重配 `sys.stdin`**。Windows 上 `sys.stdin` 默认跟随控制台代码页（cp936/gbk），管道喂进来的 UTF-8 字节被按错误编码解码，产生代理对字符。

修法（`scripts/lib/library_io.py`）：

```python
for _stream in (sys.stdin, sys.stdout):
    try:
        _stream.reconfigure(encoding='utf-8')
    except (AttributeError, ValueError):
        pass
sys.stdout.reconfigure(encoding='utf-8', newline='\n')
sys.stdout.write(serialize_library(json.loads(sys.stdin.buffer.read().decode('utf-8'))))
```

**为什么这条重要**：这不是「测试环境问题」，而是**Windows 上任何跨语言调用都会触发**。
如果只读文档的「44/44 通过」就认为自检全绿，这个缺陷会一直潜伏到 P2 切换时才暴露。

修后：**47/47 全绿**（断言数从 41 涨到 47，说明自检本身也补强了）。

### 3.2 P0-10 的 `pruneEmptyDirs` 只在「分区操作时」调用，不清理存量

`pruneEmptyDirs` 实现在 `flow.mjs:80/618/726`，挂在分区命令（submit/claim/publish）的路径上。
但那 42 个空目录是**我 publish 517 条时留下的存量**——在新实现之前产生，不会被后续任何分区操作清掉（因为已经空了，没有文件可搬）。

**P0-10 的验收标准「空目录为 0」在验收时并未达成。** 我已清理：

```bash
find data/_intake data/_review data/_draft -type d -empty -delete
# 42 → 0
```

清理后 `flow:status` 输出明显改善：
```
待入库区  _intake  14 款（dishwasher 6 / water-heater 8）
```
（清理前是 23 个品类目录，其中 17 个是空的）

**建议**：`pruneEmptyDirs` 保留（防止新增），但执行状态里的「✅ 完成」应修正为
「机制已加，存量由一次性清理处理」，避免后来者误以为已验证为空。

### 3.3 P0-7 的 `actor unknown` 暴露了一个可改进点

`flow:claim --help` 的自证输出是：

```
操作自证：数据 data/；分支 main；actor unknown
```

`actor unknown` 说明**不带 `--by` 调用时 actor 为空**。这本身符合设计（actor 是自述字段），
但配合 P0-6⑥ 的 `--from collect-wash`（按提交人批量认领），出现了一个组合场景：

`--from <actor>` 认领时，当前操作者的 `--by` 是什么？若不传，`journal` 里会记 `actor: unknown`，
**这条认领记录就不知道是谁做的**——而 P0-6 的整个目的就是让归属可见。

**建议**：`--from` 与 `--by` 至少要有一个非空；两者都缺时警告「本次操作将无法追溯操作者」。
约 3 行。

3. git 历史里可完整找回（`git show c348d86:scripts/extract-legacy.mjs`），
   删掉不损失可溯性

同时清掉 `package.json` 的 `extract:legacy` 与 README 的提及。

**保留它唯一的价值是「日后核对来源」**——但这个目的 git 历史已经更好地满足了
（能看到它被引入的提交、当时的数据、以及后续所有 `products.json` 的变更）。
