## 2. 对第 6 节问题的回答（甲方）

### 6.1 工作目录与资料可达性

1. **工作目录能否跨会话固定**：可以，且主动权在编排方。多 Agent 模式下，**子 Agent 自身从不决定 cwd——它的「仓库路径」完全由编排方注入的提示词决定**（首轮采集波我给 6 个子 Agent 的提示词都写死了 `D:\GitHub Pages\moyu929.github.io`）。worktree 模型下，编排方为每个子 Agent 注入其 worktree 绝对路径即可固定。
2. **是否从 cwd 读规范文档**：是。会话开头按序读 `AGENTS.md` → `skills/appliance-data-curation/SKILL.md` → `npm run flow:status`，全部按仓库相对路径。worktree 完整 checkout 后这些文件自动存在（方案的 git ls-files 核查与我方实践一致），无需手工播种。
3. **实际踩过的越界场景**（回答方案的追问）：
   - **最现实的向量是编排方提示词里的路径**：我给子 Agent 的提示词写死了主仓绝对路径。worktree 模型下若编排方疏忽没换成对应 worktree 路径，**整批子 Agent 会写回主树**——这不是假设，是本轮波次实际使用的模式。对策见第 4.1 节（P1-6 应增加编排方义务条款）。
   - 甲案事故 2（仓库外临时目录被清）说明跨目录触达确实存在于至少一方，但成因无法归因到具体 Agent，只能按方案的「可见性兜底」处理。
   - 我方的 6 个子 Agent 本身没有观测到目录外写入（它们的所有写操作都在注入路径之下）。

### 6.2 一行一款是否够用（补充甲方分析）

方案把此问抛给了乙方，我补充一个它没展开的技术细节——**按操作类型区分，行级合并的友好度不同**：

- **修改/替换**（B 的订正稿发布）：不同产品=不同行，三方合并干净。这是最高频操作，结论安全。
- **追加**（新品类发布）：新行插在数组尾部，两个分支同时向**同一品类**追加时，都要改「原最后一行」的逗号归属 → 会产生行冲突。
- 缓解（不需要额外机制）：a) 发布以批次 PR 为单位，同品类并发追加本身低频；b) 请求合并前 `rebase main` 是标准 git 动作，冲突当场由 B 以 change_log 裁决；c) 若实测频率高于预期，正好落入方案 P3 的触发条件（「一行一款仍频繁出现行级冲突」）。
- **结论：一行一款够用，附已知限制**。甲方两个波次 52 款全为追加型发布，若当时是多分支并行，理论上会有约 6 处尾部冲突需要 rebase——可接受，不构成提前进入 P3 的理由。

### 6.3 自研原语动机（对乙方的问题，甲方不代答）

仅补充甲方实证：两波采集 + 一轮全程观察审核方操作，未见「缺锁」场景；`flow:status` + journal 已提供全部所需可见性。

### 6.5 首批评议清单

同意全部 5 条。建议增补第 6 条：**图片流水线的写库路径与 PR 化代价**（见第 3.2 节）——`img:webp` 每次运行要回写整品类 `img` 字段，若按方案 P1-2 原文绕道 patches/flow 入库，图片补齐这一高频操作会被显著拖慢，需要显式裁决。

### 6.6 cutover

同意「在途清零 + 共同重启点」机制，不冻结任何人。当前实测在途仍为 14（待入库）+ 38（修正区），与方案快照一致。提醒：审核方 publish 节奏很快（38 款已进修正区），清零时点可能早于预期——**建议 cutover issue 现在就建好挂出来，双方各自清零后到 issue 下确认即可**，避免「清零了但没人发起切换」的空转。

## 3. 方案中预计会失败的具体环节（附依据）

### 3.1 P0-2 按字面实现会瘫痪 A→B 交接（最重要的一条）

方案 P0-2 原文：「从 journal 反查该 key 最后一次 `submit` 的 `actor`，与 `--by` 不一致则拒绝」。

正常流程里，submit 的 actor 是采集方（`collect-fridge`），claim 的 actor 是审核方（`claude-code`）——**两者必然不一致，等于每一次正常认领都要 `--force`**。首轮波次 52 次 submit / 38 次 claim 全部会被拒。推测乙案「故障 2」的原意不是这个（更可能是「A 撤回/修改与 B 认领竞争」或「重复认领」，后者已由修正区文件存在性守卫覆盖）。若按字面实现，P0-2 会成为第一个「为防错而制造的错」。修正语义见第 5.1 节。

### 3.2 P1-2「三个 Python 脚本改产出 patches / 由 flow 统一入库」操作性不成立

- Python 无法 import Node 模块，「唯一写入者 = library-io.mjs」在实现层不可达，方案实际能得到的只是「每个语言各有一份写库实现」——那就不叫唯一写入者。
- `img:webp`（shrink-images.py）是图片流水线的收尾步骤，每次运行回写整品类 `img` 字段。若强制绕道 patches → flow/apply 入库，图片补齐这类**最高频的批量操作**被拆成两段流程，操作成本反升。
- 替代方案见第 5.2 节：把「唯一写入者」放宽为「**唯一写入规范**」——格式（一行一款）、守卫（写前指纹重算）、留痕（journal 记批量条目）三要素定义清楚，Node 侧 `library-io.mjs`、Python 侧 `library_io.py` 各一个薄实现，五条写库路径全部改为调用各自语言的库。收益等同（五条路全部受同一格式+守卫约束），操作成本大降，且方案 1.3-3「消灭第二个写库者」的验收目标不变。

### 3.3 P1-5 草稿零备份与已实测的目录清理事故叠加

`_draft` 出库后，草稿只存在于 worktree 本地一份。甲案事故 2 证明工作目录可能被并发清理；worktree 化之后 worktree 目录数量变多、被误删的面变大（`git worktree remove` 若在不该执行时执行，未 submit 的草稿全灭）。**条件**：P1-8 必须加一条「草稿区不留过夜半成品——能过校验就 submit（`withdraw` 可随时撤回继续改）」，把草稿的最长暴露窗口压到一个会话内。若乙方不接受，我方回退主张：`_draft` 内容保留入库（裁定 3 的例外条款）。

## 4. 方案遗漏的问题

### 4.1 P1-6 缺「编排方义务」条款

worktree 隔离的全部前提是「每个子 Agent 被告知正确的目录」，而这件事只有编排方能做。建议 P1-6 增补：

> **编排方义务**：为每个子 Agent 显式注入其 worktree 绝对路径（含 `cd` 指令与提示词内的路径引用），禁止出现主仓路径；编排方自己发起的批量命令亦然。

这条是软隔离四条兜底之外的第五条，且是甲方案件里唯一实测发生过的越界向量（提示词写死主仓路径）。

### 4.2 图片流水线写库路径需要显式裁决

如 3.2 所述，`img:webp` 的回写如果按 P1-2 原文走 patches，操作性不成立；按 5.2 的「写入规范」走，则它继续直接写库——那么需要明确：**图片回写走分支+PR，还是作为例外直接写 main？** 我方建议：走分支+PR（它本来就以品类为批次，天然适合批量 PR），紧急情况走「紧急修改」通道。

### 4.3 P1 与 P2 之间有一个「无 CI 合并空窗」

P1 落地后即允许分支/worktree 工作流，但 CI 与分支保护要等 P2。空窗期内「合并」退化为用户本地手工操作，需要写明：**CI 就绪前，用户本地合并任何分支前必须跑 `npm run check`**（现行纪律沿用），避免空窗期成为质量真空期。

### 4.4 schema PR 与数据 PR 的合并顺序

裁定 8 说「schema 变更单独成 PR」，但没约束依赖关系：采集分支若把新品牌加进 `groupBy.order`（本波 6 个品类都发生了），数据 PR 与 schema PR 是**同分支携带**还是**分开**？建议明确：schema 改动随数据 PR 携带但**必须单独成 commit**（评审时一眼可见、必要时单独摘出）；跨 PR 依赖时，数据 PR 合并前 rebase 到 schema PR 之后，CI 按合并后状态校验。

### 4.5 PR 正文自动汇编（降低 5.4 的操作成本反对意见）

批次 PR 的正文建议从 journal 批次条目自动汇编：来源链接清单、verify_status 分布、放弃型号及原因。这直接回应方案 5.4「B 的操作成本增加」——PR 不只是门，也是审核报告的载体，可省掉 `docs/audit/` 里的一半手写工作。建议并入 P0-3（batch id 已具备）或 P2-4。

### 4.6 journal 轮转（可选，非本轮）

journal 已 1667 条且 union merge 后只增不减。`flow:status`/`log` 目前无压力，**不建议现在做**；仅当 status 聚合变慢时按月轮转为 `journal-YYYY-MM.jsonl`（flow:status 顺序读取即可）。记录在此防止将来被当成「没考虑过」。

## 5. 对反对条的替代方案

### 5.1 P0-2 归属校验的修正语义

原义（按字面）会拒掉全部正常认领。替代：

> `flow:claim` 校验：**claim 的 `--by` 不得等于该 key 最近一次 `submit` 的 actor**（禁自采自审）；「已被认领」仍由修正区文件存在性守卫；journal 的 claim 条目增加 `submitActor` 交叉引用字段；`--force` 保留，用于用户明示的单人双角色模式，journal 记 `forced:true`。

这样乙案「故障 2」关心的所有场景（自采自审、重复认领、竞争认领）全部有守卫，且正常交接零摩擦。**另请方案向乙方核实「故障 2」的原意**——如果原意是「A 在 B 认领后仍可 withdraw」类竞争，那属于时序竞争，应由 withdraw 的文件存在性检查 + 指纹守卫覆盖，不需要归属校验。

### 5.2 P1-2「唯一写入者」改为「唯一写入规范」

> 定义库写入三要素：① 一行一款序列化；② 写前对磁盘现文件重算指纹，与载入时不一致即拒绝（P0-1 同款）；③ 写入动作记 journal（批量条目）。
> 落地为两个薄实现：`scripts/lib/library-io.mjs`（flow.mjs、mi-store.mjs、validate 用）与 `scripts/lib/library_io.py`（classify-facets.py、import-brands.py、shrink-images.py、fill-*.py 用）。
> 验收标准不变：五条写库路径全部收敛到两个实现，`git log -p data/*/products.json` 中不再出现格式横跳。

### 5.3 P1-3 降级为可选

P0-1 守卫 + P1-1 格式已消灭丢失成因；行级替换只优化 diff 大小。建议 P1 验收不含此项，实现排期放在 P2 之后、以「git diff 噪音实测 bothersome」为触发。
