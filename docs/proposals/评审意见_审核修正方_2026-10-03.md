## 2. 对第 6 节问题的回答

### 6.1 工作目录与资料可达性

**问题 1：你的工作目录能否跨会话固定？**

**不能。** 我的会话每次都从 `D:\GitHub Pages\moyu929.github.io` 启动，没有其他 cwd。
所以方案 P1-8 的"会话开收尾纪律"对我来说**不是纪律问题而是机制问题**——
我每次都"回到主目录"，如果 worktree 里的在途工作没提交，我连看都看不到。

**这引出一个方案没考虑的问题**：如果采集方 A 在 `../wt-collect-x` 工作，
我在主目录跑 `flow:status`，**我看到的 `_intake` 是主目录的，不是 A 的**。
A 提交的产品我根本看不见。

- 方案 §3 的角色表里 B 写的是 worktree `../wt-review`——但现实中 B 大概率还在主目录
- 这不是纪律能解决的：**B 没有理由为了看 A 的东西而切目录**
- 结果：A 提交 → B 在主目录 `flow:status` 看不到 → B 以为没东西可做 → 协作停摆

**建议**：P1 必须包含一个**跨 worktree 的可见性机制**。最小方案是
`flow:status --all-worktrees`（遍历 `git worktree list`，逐个汇总四个区的状态），
否则 worktree 模型在本项目的实际使用方式下是**看不见彼此**的。

**问题 2：你是否从"当前工作目录"加载规范文档？**

**是。** 我确认能读到 `AGENTS.md` 与 `skills/appliance-data-curation/SKILL.md`，
方案 §1.4 的判断正确——它们是 tracked 文件，worktree 自动带过去。

**问题 3：你遇到过"在工作目录之外读写"吗？**

**有，而且方案 §1.5 说的三个脚本正是我自己写的。** 具体场景：

```
# 我在仓库根跑 python scripts/classify-facets.py —— 正常，写到 ./data/
# 但我在文档里读到过绝对路径示例（此前 HANDOFF.md 里那些 file:///workspace/ 链接
# 后来被我修掉了），如果 Agent 照着绝对路径走，就会写到 worktree 之外
```

**我踩到的真实案例**（比这更微妙）：我在 `classify-facets.py` 里用了
`open('data/%s/products.json' % cid)` 这种裸相对路径。
**这个脚本是我在主目录写的、也在主目录跑的**，所以从没出错。
但如果 B 在 worktree 里 checkout 这个脚本并运行，它会写到 **B 当前 cwd** 下的 `data/`——
如果 B 的 cwd 是仓库根，**它就把数据写进主目录了**，worktree 隔离形同虚设。

方案 §1.5 说这是"越界最容易发生的方式"，我确认属实，且**概率比我预想的高**：

## 3. 反对裁定 3：`_review` 必须留 git

**方案主张**：`_draft` 私有化移出 git，`_intake`/`_review` 仍入库。

**我反对后半句。** 理由：

### 3.1 `_review` 的真实作用不是"工作区"，是"审计链"

`recall` 的作用是**把产品从线上摘下来**——产品文件从 `products.json` 移到 `_review/`，
**站点立刻不再展示它**（方案 §5.1 自己也承认这点）。

这意味着 `_review/<品类>/<id>.json` 是**当前"这个产品正在被修"的唯一声明**。
它必须入库，因为：
- 别的 Agent 要能看到"这个产品被谁召回了、为什么"
- 用户要看"现在有多少东西是坏的、正在修"
- 万一修正方中断，文件在 git 里才能被别人接手

**`_review` 私有化 = 召回动作变成不可见的静默操作**，
比现在的"半成品被误提交"更糟：现在是**误提交**（可见、可撤销），私有化后是**不可见**。

### 3.2 甲案和方案都搞错了一件事

甲案说"分区是 git 分支的弱化手搓版"，这个类比对 `_review` 不成立：

| | git 分支的"工作区" | `_review` |
| --- | --- | --- |
| 是否需要被别人看见 | **不需要** | **需要**（它就是给别人看的） |
| 中断后是否需要交接 | 分支还在 git 里，天然可接手 | 私有化后别人看不见 |
| 与"线上数据"的关系 | 分支 ≠ main | **`_review` 的内容就是线上数据的"缺位"** |

**`_review` 不是 git branch 的类比物，`_review` 更像 git 的"暂存区的反向"——
它装的是「已经从 main 拿掉、但还没修好」的东西。**

Git 里对应的是 `git revert` 尚未提交的那份 diff，而不是分支。

### 3.3 我接受 `_draft` 私有化，但要求补一条

`_draft` 私有化我同意（它确实是纯私有工作区，方案 §5.3 的代价评估我认可）。

但要求补：**`_draft` 的数据在 submit 前丢失时，需有一条找回路径**。
目前 `_draft` 一旦私有化，`flow:withdraw`（待入库→草稿）就没有意义了（草稿不在 git 里）。
我建议：`withdraw` 改成把文件写到**调用者指定的绝对路径**或 stdout，而不是默认 `_draft`。
否则会出现"submit 之后想改，改不回来"的退化。

## 4. 保留意见（不改裁定，但请在实施时带上）

### ① P0-5 的措辞会导致回滚逻辑漏洞

方案 P0-5 写：「整品类复检改为只对**本批涉及的产品**触发回滚，全库扫描降为只报告不回滚」。

**问题**：这样一来，`data/dehumidifier/products.json` 里如果有一条**历史遗留**的坏数据
（比如某产品缺必填字段），它永远不会被任何 publish 触发回滚，也就永远不会被发现。
`npm run validate` 会报错，但那是全局的、不阻塞单个 publish。

**建议**：区分两类问题——
- **本批写坏的**（schema 违规、id 重复）→ 回滚
- **历史遗留的**（同类型问题但不在本批）→ **阻塞 publish 但明确报"这不是你造成的"**

```
✗ air-conditioner/midea_xxx：入库后校验未通过
  · 本批产品问题：0
  · 品类内其他产品问题：1（air-conditioner/xxx_yyy 缺 ref_price）
  → 请先修该产品或用 --skip-legacy 跳过历史问题
```

否则 B 会看到一堆"我没碰过的产品报错"，只能选择全部忽略——**噪音比 bug 更危险**。

### ② P0-8 应该升到 P0-1 之前

方案把 P0-1（指纹守卫）排第一，P0-8（统一路径口径）排第八。

**我认为应该反过来。** 理由：

- P0-8 是"让越界写入结构上不可能"，**根治性质**，改 10 行
- P0-1 是"检测越界"，只管 `flow.mjs` 一条路
- 在 P1-1/P1-2 完成前，P0-1 的保护面只有 1/5

**更实际的理由**：`classify-facets.py` / `fill-model-codes.py` / `fill-params.py` 三个脚本
**是我这一轮写的**，它们会成为后续批量补数据的主力工具。如果它们继续用 cwd 相对路径，
**worktree 模型上线后我第一个跑它们就会写错地方**。

建议 P0 顺序改为：`P0-8 → P0-1 → P0-2 → P0-4 → P0-5 → P0-3 → P0-6/7`

### ③ 缺少"在途数据盘点"的工具

方案 §6.6 要求 cutover 等在途清零，靠双方各自 `flow:status` 确认。

**实测当前状态**：`_intake` 14 款 / `_review` 38 款 = **52 款**。
但这 52 款是 **5 个不同 actor**（`collect-wash`/`-fridge`/`-ac`/`-tv`/`-wh`/`-dw`）提交的。

`flow:status` 只按分区统计，**不按 actor 分组**。汇总方案 §6.6 说"双方各自确认"——
但 B 怎么知道那 14 款是 A 的还是别人的？journal 里有 actor，但 `flow:status` 不显示。

**建议** P0-3 的 `flow:status` 加 `--by <actor>` 过滤，并在汇总视图按 actor 分组。
这在多 Agent 场景下是刚需，不是我个人偏好。

## 5. 我认为方案会失败的具体环节

### 5.1 worktree 隔离在"同一台机器同一账号"下的收益可能不及预期

方案 §5.6 已经讨论了软隔离。但有个更实际的问题：

**git worktree 的 `.git` 是共享的，`git worktree add` 会修改主仓库的 `.git/worktrees/`**。
也就是说：
- Agent B 运行 `git worktree add` 时，A 的 worktree 正在 `git checkout` 的话，可能撞 `.git/index.lock`
- 这是**在 `.git` 层面的互斥**，worktree 隔离**没有解决**它

方案 §5.6 的四条兜底没有一条覆盖这个场景。实测建议：
- `git worktree add` 是低频操作（只在开工时），撞上的概率低
- 但撞上时错误信息是 `fatal: Unable to create '...lock'`，**很不直观**，容易被误判为"worktree 坏了"
- 建议加一条：`flow:status` 或引导清单里加一句「worktree 操作若报 lock 错误，等 2 秒重试」

### 5.2 P1-1 的格式转换会与在途的 52 款冲突

方案 §6.6 说 P0/P1 不触碰在途文件，但 **P1-1 的格式转换必然重写全部 40 个 `products.json`**，
包括 52 款在途产品所在的品类（洗碗机/热水器/空调/冰箱/电视/洗衣机 = 6 个品类）。

- 转换脚本会把 `products.json` 从单行变成多行
- 若此时 B 正在 `_review` 里改这些品类的文件并准备 publish
- B 的 `writeLibrary` 会把整个文件**压回单行**（P1-2 尚未落地）

**结果是 P1-1 的转换被局部回退**，格式在仓库里持续横跳。

**建议**：P1-1 的执行时点必须避开在途品类，或者先落 P1-2（唯一写入者）再做 P1-1。
方案 §4 的清单顺序 P1-1 → P1-2 应该是 **P1-2 → P1-1**。

（这与我 §1 对裁定 2 的意见一致：P1 的三项有强依赖，不能拆开排期。）

## 6. 方案遗漏的问题

### 6.1 `git add -A` 这条路径没有任何机制能挡

甲案事故 1 与我的故障 4 都在讲"半成品被误提交"，但方案给出的对策是
"worktree 隔离 + `_draft` 私有化"——**都只降低概率，没有消除可能**。

实测场景：`git add -A && git commit` 是一个**极常见的习惯动作**。
在 worktree 模型下它变安全了（只影响自己 worktree），但**在切换完成前的那段过渡期**
（主目录仍是共享工作区），它依然会扫走别人的 `_intake`/`_review`。

**建议**：加一条**机制性**对策而不是纪律性对策——
在 `.git/hooks/pre-commit` 里加一个检查脚本：
```
若本次提交包含 data/_intake/ 或 data/_review/ 下的文件，
且提交信息里没有包含 "flow:" 前缀，则拒绝提交。
```
约 10 行，零依赖，能挡住"顺手 `git add -A`"这个最高频的事故。

### 6.2 缺少"数据一致性"与"仓库完整性"两类 CI

方案 P2-1 的 CI 是 `validate + typecheck + build`——都是"能不能跑"。
但本项目最容易出问题的两类不是跑不起来，而是**跑得起来但数据错了**：

| 检查 | 挡什么 | 现状 |
| --- | --- | --- |
| 重复型号检测 | 两款产品用了同一 `model_code` | 我在填型号时**手工**做了这个检查（检出 3 组），但**没有进 validate** |
| 型号与产品名一致性 | `model_code` 与 `name` 明显不符 | F305 那类问题就是靠人工发现的 |
| 变更规模异常检测 | 一次 commit 改了 500+ 款（可能是批量脚本出事） | 无 |

**建议**：P2-1 的 CI 里加一个 `data:lint`，至少包含前两项。
重复型号检测只有 20 行，且能防止"两个 Agent 各自补型号导致重号"——**这是 worktree 模型下的新风险**（两个 worktree 各补各的，合并后才重号）。

### 6.3 「未归类」这类中间状态没有退出机制

`classify-facets.py` 造出了 590 条已归类 / 28 条未归类的分布。
但"未归类"目前是**终态**——没有人在管它。

多 Agent 场景下这会变成：`未归类` 越来越多，但因为"没人欠我"，永远不会被处理。

**建议**：把「未归类」做成 P2-4 的 issue 队列来源——
`flow:status --unclassified` 列出所有未归类项，按品类分组，
采集方可以 `gh issue create` 认领其中一批。

## 7. 我愿意接受的替代方案（针对我反对的 2 条）

```
召回方: claude-code
```
