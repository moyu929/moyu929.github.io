# 工作流升级意见书（采集编排方视角）

- **作者身份**：采集/编排方 Agent。**利益声明**：现行「分区流转协议」（`AGENTS.md` 第 3 节）与 `scripts/flow.mjs` 由我设计实现；2026-10-03 的首轮多品牌采集波（6 品类 / 52 款）由我编排。下文对现行协议既有辩护也有批评，请总结方注意此立场。
- **写作目的**：与审核修正方 Agent 的意见书并列，供第三方 AI 汇总、裁决并产出可实行方案。
- **建议归档约定**：同目录下以 `docs/proposals/工作流意见_<角色>_YYYY-MM-DD.md` 命名，便于集中比对。
- **写作日期**：2026-10-03

---

## 1. 一句话立场

分区流转协议解决了它要解决的问题（A/B 互扰、半成品被划入审核），但它是在**单工作树**里手搓的一套「分支系统」；本项目要走向「多采集 × 多修正 × UI 开发」的团队模式，正确方向是**把这套手搓机制下沉到 git/GitHub 原生机制**（分支、worktree、PR、Issues），flow 工具链与分区文件格式保留为分支内的操作规范，而不是在目录协议上继续叠加。

---

## 2. 实测证据：什么在起作用

以下均有可复核的仓库痕迹，不是推测：

| 事实 | 证据 |
| --- | --- |
| 6 个审核标注字段 + flow:submit/publish 关口校验，把「没来源的数据」挡在了入库前 | 本波 52 款全部带 `verify_status/verify_url/change_log`；可疑值（噪音截断、热负荷矛盾、分仓容积反常）被写 `查不到` 并留剔除理由 |
| 分区物理隔离让「采集方永不见修正中的数据、修正方拿不到半成品」成立 | 首轮 52 款经 `draft → intake` 提交，审核方数小时内认领 38 款，全程零互扰；流转日志 `data/_flow/journal.jsonl` 完整可溯 |
| 审核方已把新协议用于真实纠错 | journal 有 `recall → publish` 把松下 FV-30BQS1 从 heater 挪到 bath-heater 的记录（2026-10-02） |
| schema 驱动让数据扩量不需要前端改动 | 本波新增 15 个品牌只改 schema.json 的 order/colors |
| 校验脚本（validate）是可靠的质量底座 | 本波全部 `npm run validate` 通过；「数据校验通过」与实际可用性一致 |

**吞吐量基线**：本波 52 款 ≈ 2 个并发采集 Agent × 数小时（含网络取证）。全站还有 15 个小米独占品类，若目标规模是数千款多品牌数据，按此基线需要几十波任务——**效率必须来自「任务可切分、可断点续跑、可并行」，而不是指望单次大并发**。

## 3. 实测事故清单（这是提方案的主要依据）

1. **共享 git index 互扫**：审核方提交 `f48d2f6` 时把我**写到一半**的 AGENTS.md / package.json / validate-data.mjs 一起扫进其提交，同时**漏掉**了已被引用的 `scripts/flow.mjs` 与 `scripts/lib/`——HEAD 一度对新克隆是坏的（`npm run flow:*` 与 `validate` 缺依赖文件）。目前靠「提交时显式 pathspec」的纪律规避，纪律在多方下必然失守。
2. **共享工作树的清理误伤**：我的冒烟测试临时目录在两轮命令之间被并发清理删除过一次。
3. **半成品互相可见**：审核方未提交的 `products.json` 改动长期躺在工作树，采集方跑校验时看到的是别人的中间态。
4. **平台并发限额是硬约束**：一次性派 6 个子 Agent 直接 `user concurrency limit exceeded`；实测稳定形态是 2 个并发。这不可绕过，只能靠任务队列消化。
5. **单行 products.json 的合并灾难**（尚未发生，但结构必然）：全库 1036 款在一个压缩单行 JSON 里。当前「只有 B 写库」掩盖了它——**一旦有第二个修正方，同品类并行发布就是单行文件上的读-改-写竞争，后写覆盖先写，git 无法合并**。
6. **流转日志将成为合并热点**：`journal.jsonl` 单文件追加，多方并行时每次 pull 都可能冲突。
7. **发现的问题没有落脚点**：本波发现「存量 4 款海尔冰箱实为冷藏柜（当初抓自太平洋错误分类页）」「热水器 power 字段新旧口径不一致（仅电功率 vs 热负荷+电功率）」——这两件事目前只存在于对话与提交信息里，没有议题可追踪、没有决定记录可引用，下个会话即失忆。
8. **没有评审门**：`flow:publish` 直通库，push 即部署。批量入库前没有一张「可看 diff、可评论、可打回」的单子。

## 4. 根因归纳

| 症状 | 根因 | 现行协议为何管不了 |
| --- | --- | --- |
| 提交互扫、坏 HEAD | 所有 Agent 共享**一个工作树 + 一个 git index** | 分区只隔离了文件路径，没隔离 git 状态 |
| 多修正方不可并行 | products.json 单行数组，合并粒度=整文件 | 协议里「B 唯一写库」实际是「单修正方」假设 |
| 断点续跑靠人脑记忆 | 没有仓库内的任务队列（Issues） | HANDOFF.md 是叙事日志，不是可认领的工作单元 |
| 入库无评审门 | flow:publish 直通 main | PR 这一层缺失 |
| 跨方通信靠汇报 | 没有议题/评论区 | journal 只记动作，不承载讨论 |
| UI 开发与数据开发的耦合 | push main 即部署，main 无保护 | 任何一方的 WIP 都可能被一起部署 |

## 5. 我的主张：协作机制迁移到 git/GitHub 原生，目录协议下沉为分支内规范

**核心判断：分区目录是 git 分支的弱化手搓版。** 分支=物理隔离，worktree=每 Agent 独立目录+独立 index，PR=待审队列+评审门+讨论区，merge=入库，revert=回滚，Issues=任务队列+议题区。不需要再造一层自研轮子，需要的是把现有的东西接到原生机制上。

### 5.1 目标角色模型

| 角色 | 工作位置 | 动作序列 | 边界 |
| --- | --- | --- | --- |
| 采集方 ×N | 分支 `collect/<任务号>-<品类>`，各自 `git worktree` 独立目录 | 分支内走 `flow:submit` → 推分支 → 开 PR（PR 即「待入库批次」） | 只开 PR，永不直接改 main；不碰他人分支 |
| 修正方 ×N | `gh pr checkout` 认领 PR 分支 | `flow:claim` → 核对/订正 → `flow:publish`（在分支上）→ 推回 → 请求批准 | 一个 PR 一个负责人；跨 PR 同产品冲突=git 真冲突，以 change_log/溯源裁决 |
| UI 开发方 | 分支 `feat/<主题>` | 改 `src/**` → 开 PR → CI 过 → 合并 | 与数据 PR 天然无文件交集；main 受 CI 保护 |
| 用户 | GitHub 网页（或本地合并） | 看板、批准 merge、裁决冲突、定口径 | merge 权限只在用户，或明确授权给某 B |

### 5.2 支撑这个模型的关键小改动（按性价比排序）

1. **products.json 改为一行一款**（每个产品对象占一行）。这是全局收益最大的单点改动：多 PR 并行发布同一品类时 git 按行自动合并；真正的冲突只剩「两个 PR 改同一款产品」——而这恰恰是需要人裁决的合法冲突。转换用一次性脚本，validate/flow 兼容性回归半天内可完成。
2. **`.gitattributes` 给 `data/_flow/journal.jsonl` 设 `merge=union`**：追加型日志在分支合并时自动保留双方条目，冲突类别直接消失。
3. **CI 门 + 分支保护 main**：PR 必须过 `validate` + `typecheck` + `build` 才可合并；main 禁止直推。数据坏不了站，UI 半成品进不了 main，push 即部署的耦合被解开。
4. **Issues 作为任务队列与议题区**：每波采集=一个 milestone；每条任务/缺陷/口径问题=一个带 label 的 issue（建议标签：`采集任务` / `数据缺陷` / `口径决定` / 品类名）。各 Agent **会话开始先 `gh issue list` + `gh pr list` 认领**——断点续跑从「重建记忆」变成「认领下一条」。本波遗留的两件事（海尔冷藏柜、power 口径）应立为首批评议。
5. **flow 工具链全部保留**：submit/claim/recall/publish/return/drop 语义不变，只是从「跨目录搬文件」变成「分支内的关口」。分区目录（_draft/_intake/_review）继续作为分支内的文件载体与校验钩子。已验证 flow.mjs 基于脚本自身路径解析根目录，天然 worktree 兼容。
6. **数据版本化**：合并即版本；批量入库打 tag（如 `data-20261003`）；回滚=revert merge commit；PR 历史即数据变更史（谁、何时、依据什么来源改了哪款）。
7. **离线兜底**：协议按「git 必选、GitHub 可选」设计——无 `gh`/断网时，PR 退化成本地分支合并，Issues 退化成 `docs/board/*.md` 票据文件。

### 5.3 明确反对的方向（供总结方对照）

- **自研议题/看板系统**（在仓库里造 ticket JSON + 状态机）：Issues 免费提供同样能力且人类可直接参与；自研版本等于第二个 journal，维护成本高、可见性差。
- **立即重构为「每产品一文件」的库格式**：合并友好度最优，但要动 src/data.ts、全部脚本与图片流水线；在一行一款已解决按行合并的前提下，收益/成本比不划算。留作单品类产品数涨到数百行时的 Phase 3。
- **回到快照锁式「看门」工具或引入实时互斥**：分支隔离已经结构性消灭了需要看门的场景。
- **为「多 Agent 通信」自建消息通道**：PR/issue 评论区 + @提及 + 有约定的会话开头检查（issue/pr list）已覆盖「采集方补证据 ↔ 修正方提问」的实际通信需求。

## 7. 开放问题（请总结方重点裁决）

1. **merge 权限**：只归用户，还是默认用户 + 授权修正方代批？建议：先只归用户，跑顺后再授权。
2. **库格式路线之争**：若修正方意见书主张「每产品一文件」，请评估迁移面（前端 glob、mi:apply、validate、flow、图片流水线）与收益差，在一行一款先行、文件化后置的渐进路线上做取舍。
3. **分区目录是否保留**：我主张保留（作为分支内载体与关口校验钩子，迁移成本低）；若总结方认为分支化后分区冗余，请给出 submit/claim/publish 关口校验的新挂载点（PR CI check）。
4. **无 gh CLI 期间的任务队列形态**：Phase 2 前用 `docs/board/*.md` 票据过渡，还是先装 gh 再启动协作切换？
5. **审核方的迁移成本**：其正在用分区协议做真实修正（journal 有记录），切换需要一个无在途任务的时点——请给出切换协调机制（如一个 `cutover` issue，双方确认在途批次归零后切换）。
6. **本地多 Agent 的资源模型**：每个 Agent 一个 worktree（共享 .git），还是每个 Agent 一个克隆（完全隔离）？前者省磁盘但 index 锁仍共享度低（worktree 的 index 是独立的，锁不冲突），后者最干净但需要多次 fetch。我倾向 worktree。

## 8. 给总结方的提示

- 我与审核方意见书最可能分歧的点：**库文件格式**（一行一款 vs 每产品一文件）、**分区目录去留**、**flow 工具链保留范围**。分歧三者的共同本质是「自研工具 vs 原生 git 的边界画在哪」，建议总结方用一个统一原则裁决：**凡是 git/GitHub 原生已提供的，不重造；凡属本仓库数据质量语义的（来源优先级、审核字段、异常阈值、关口校验），保留在自研工具里。**
- 请把「平台并发限额（实测 2 并发）」当作硬参数纳入方案：任何依赖大并发的路径都不可行，任务粒度与断点续跑是效率主轴。
- 事故清单（第 3 节）与吞吐量基线（第 2 节）均有仓库痕迹可核（提交 `f48d2f6`/`7f3e226`、journal、本波 PR 式提交序列），总结方可直接引用，不必采信我的转述。
