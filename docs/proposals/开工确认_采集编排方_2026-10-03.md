## 2. 开工前必须记录的 4 条实施约束（不阻塞开工，但验收要含）

### 2.1 P0-8 钩子必须「随仓库走」，否则只在一台机器上存在

`.git/hooks/` 不被 git 跟踪。要求：

- 钩子脚本入库（建议 `scripts/hooks/pre-commit`），`npm run hooks:install`（或文档化 `git config core.hooksPath scripts/hooks`）写进引导清单；
- **P0-8 验收必须含一项**：新克隆（或新 worktree）执行安装动作后，`git add -A` 一个含 `_intake` 文件、信息无 `flow:` 的提交**被拒**；
- 已知边界如实记录：pre-commit 对 merge 提交不生效，钩子是本地防线，真正的门是 P2 的 CI——两者不能互相替代。

### 2.2 P1-1「规范化序列化器」的跨语言陷阱（全方案最可能静默失败的一处）

「同一产品对象在任何写入者下产生逐字节相同的文本」在 JS 与 Python 之间有三个已知差异，必须显式钉死并做**双向一致性测试**（同一组对象分别经 `library-io.mjs` 与 `library_io.py` 序列化，断言逐字节相等）：

| 差异 | 现象 | 处理 |
| --- | --- | --- |
| 浮点格式 | `json.dumps(399.0)` → `399.0`；`JSON.stringify(399)` → `399`。**库内实测存在 `official_price: 399.0`**（heater 现文件原文） | 规范：整值浮点一律输出为整型。两侧各自实现（JS 天然满足；Python 在序列化前归一化或自定义 float 编码） |
| 非 ASCII 转义 | Python 默认 `ensure_ascii=True` 输出 `\uXXXX`；JS 输出原文 | 两侧统一 `ensure_ascii=False` / JS 默认 |
| 分隔符与键序 | Python 需显式 `separators=(',', ':')`；键序两侧都按解析序保留 | 钉死为紧凑分隔符 + 解析序键序 |

不做这一条，P1-2 转换后任何一次 Python 侧写入都会把 `399` 改回 `399.0` 之类的字节漂移，格式横跳以更隐蔽的方式复发。

### 2.3 P0-3 的重试不能吞掉真冲突

`EPERM/EBUSY` 重试（Windows 文件锁）与**指纹不一致**（真并发写）是两类失败：前者可退避重试，后者必须立刻报错退出。实现时两者不得共用同一条重试路径，否则守卫会被重试逻辑架空。

### 2.4 P1-5 的 PR 化部分随 P2 生效，需要一条过渡规则

P0/P1 仍是共享树模式，「库内产品图片回写走分支 PR」还不存在。过渡规则：P2 合并前，图片回写经 `library_io` **直接写当前模式下的库**（等价于现状 + 新守卫）；P2 切换后自动升级为分支 + PR。请在 P1-5 条目里补注这句话，避免执行者在 P1 阶段等待不存在的 PR 通道。
