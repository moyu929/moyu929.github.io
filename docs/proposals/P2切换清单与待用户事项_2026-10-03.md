## 三、附录：待插入 `AGENTS.md` 的「分支协作协议」章节（草稿）

> 切换前不要插入本节。以下为切换时使用的正文草稿。

```markdown
## 3.5 分支协作协议（P2 切换后生效）

分区仍是数据形态的载体，但**传输与合并交给 git 原生机制**：

| 角色 | 工作位置 | 动作 | 硬边界 |
| --- | --- | --- | --- |
| 采集方 A | worktree `../wt-collect-<任务号>`，分支 `collect/<任务号>-<品类>` | 分区流程 → `flow:submit` → 推分支 → 开 PR | 只开 PR；不碰 main；不碰他人 worktree |
| 修正方 B | 主目录（本机无法固定 cwd），可切分支 | `gh pr checkout <PR>` → `flow:claim` → 核验修正 → `flow:publish` → 推回 → 请用户合并 | 不得直推 main |
| 用户 | GitHub 网页 | 批准 merge、裁决冲突与口径、定剔除 | merge 权只在用户 |

- **PR 合并 = 上线时刻**。合并前站点展示上一个已发布版本；`recall` 不再立即下架。
- 一个 PR = 一个批次（一波采集 / 一批召回），不是一个产品一个 PR。
- 分支命名：`collect/<任务号>-<品类>` / `review/<批次号>` / `feat/<主题>` / `fix/<主题>`。
- **编排方义务**：为每个子 Agent 显式注入其 worktree 的绝对路径，**禁止在提示词里出现主仓路径**
  （这是唯一被实测确认发生过的「越界写入」向量）。
- schema 变更随数据 PR 携带，但**必须单独成一个 commit**；影响已有产品的语义变更单独开 PR。
- 冲突裁决：同品类不同产品 → git 按行自动合并（库文件已是一行一款）；
  同一款产品被两处改 → 真冲突，以 `change_log` 与溯源依据裁决。
- 会话开头先 `gh pr list` / `gh issue list` 认领任务，再 `npm run flow:status` 看分区现状。
```
