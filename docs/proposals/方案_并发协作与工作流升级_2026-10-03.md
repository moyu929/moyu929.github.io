### 1.3 两份意见书**都没提到**、但我认为更关键的一条

**"只有 B 经 `flow:publish` 写库"这条铁律，在工具层面从来没有成立过。**

实测有 **5 条写库路径**（不止 `flow.mjs` 一条）：

| 写入者 | 位置 | 写出的格式 |
| --- | --- | --- |
| `scripts/flow.mjs` | `writeLibrary()` [:73](../../scripts/flow.mjs#L73) | 紧凑**单行** |
| `scripts/mi-store.mjs`（`mi:apply`） | 字节级文本补丁 [:165-181](../../scripts/mi-store.mjs#L165-L181) | 保持原格式 |
| `scripts/classify-facets.py` | `json.dump(..., separators=(',',':'))` [:589-591](../../scripts/classify-facets.py#L589-L591) | 紧凑**单行** |
| `scripts/import-brands.py` | `write_products()` [:72-76](../../scripts/import-brands.py#L72-L76) | **一行一款** |
| `scripts/shrink-images.py` | `write_products()` [:39-43](../../scripts/shrink-images.py#L39-L43) | **一行一款** |

三点推论，直接改变本方案的排期：

1. **乙案故障 1（静默覆写）的风险面比它自己估计的更大**——覆写不止发生在 `publish`，任何一次 `classify-facets.py` 或 `img:webp` 重跑都是一次整文件覆写。
2. **甲案 P1-1（一行一款）的成本被高估了**：这个格式**不是要引入的新格式**，它是 `shrink-images.py` / `import-brands.py` 一直在写的格式，只是被 `flow.mjs` 和 `classify-facets.py` 又压回了单行。也就是说仓库里的库文件格式**本来就在两种形态间反复横跳**（`git log -p data/*/products.json` 可见）。改造成本我估为 P0 量级，不是半天。
3. 因此"消灭第二个写库者"必须成为 P1 的显式验收项——否则加了乐观锁也只在 `flow.mjs` 这一条路上生效，另外四条路照样静默覆写。

### 1.4 运行环境约束（用户 2026-10-03 已确认）

这两条直接决定 P1-6 / P2 的形态，是本方案**唯一的外部依赖**（用户 2026-10-03 已确认，故不再是待决项，而是设计输入）：

1. **可以为每个 Agent 指定不同工作目录，但不是强制约束**——仍有**小概率**发生在工作目录之外读写。因此隔离是**软的**：结构上减少相互踩踏，但工具层必须能兜住"越出目录"的少量情况（设计见 5.6）。
2. **Agent 默认只能读到工作目录内的内容**——所以每个工作目录必须自带完整的项目资料。这一条的实际情况比字面乐观，需要分清哪些**自动带过去**、哪些**不会**：

| 类别 | 是否随 worktree 自动获得 | 依据 / 处理 |
| --- | --- | --- |
| `AGENTS.md` / `README.md` / `HANDOFF.md` / `skills/**` / `docs/**` | ✅ 自动（都是 tracked 文件，`git worktree add` 是完整 checkout，共 626 个 tracked 文件） | `git ls-files` 实测 |
| 客户端技能指针 `.trae/skills/**`、`.claude/skills/**` | ✅ 自动（**也在 git 里**） | `git ls-files .trae .claude` 实测 |
| 工作区规则（`AGENTS.md` 被客户端当 always-applied rules 加载） | ✅ 自动，只要新目录被作为工作区打开 | 行为一致 |
| `node_modules/` | ❌ 不会（gitignored）；`package-lock.json` 在库里 | 每个 worktree 各跑一次 `npm install` |
| `data/_cache/**`（894 个文件 / 2.71MB，含 `miot-*.json` 型号索引） | ❌ 不会（gitignored） | 复制过去即可（2.71MB）；重爬 miot 索引要 ~2585 次请求，不值得重来 |
| `data/_draft/**` | ❌ 不会（P1-5 后才成立） | 设计上就该如此：草稿是各 Agent 私有的 |
| **客户端项目记忆 / 会话历史** | ❌ **不会**——记忆目录是按**项目路径**派生的（本机为 `…/projects/-d-GitHub-Pages-moyu929-github-io--p2-…`），换到 `D:\GitHub Pages\wt-xxx` 就是另一个项目键 | **这是本方案最需要注意的副作用**，对策见 5.6-③ |

> 结论：用户担心的"文档缺失"在 worktree 模型下**基本不成立**（规范文档全是 tracked 文件，会自动带过去）；真正会丢的是**运行依赖（`node_modules`）、抓取缓存（`data/_cache`）与客户端侧记忆**。前两者是引导清单里的一次性动作，第三者需要一条纪律而不是技术手段。

### 1.5 顺带查到的一处"越界"成因：根目录解析口径不统一

针对 1.4 约束 1「小概率在工作目录外读写」，我把 `scripts/` 下的路径解析口径全查了一遍：

| 口径 | 脚本 | 在 worktree 模型下是否安全 |
| --- | --- | --- |
| 按**脚本自身位置**解析（`import.meta.dirname` / `pathlib.Path(__file__)`） | 全部 Node 脚本（`flow.mjs`、`mi-store.mjs`、`validate-data.mjs` 等）+ 7 个 Python 脚本（`import-brands.py`、`shrink-images.py`、`pconline-specs.py`、`fetch-facet-evidence.py` 等） | ✅ 安全：脚本只能写自己所在的 worktree |
| 按 **cwd** 解析（裸相对路径 `data/<品类>/products.json`） | **至少 3 个**：`classify-facets.py`、`fill-params.py`、`fill-model-codes.py` | ⚠️ 只在"从预期根目录调用"时安全；**从别处的 cwd 调用就会写到别处**——这正是"越界"最容易发生的方式 |
| 硬编码绝对路径 | **无** | — |

好消息：没有硬编码绝对路径，所以**只要统一口径，"越界写入"在脚本层面可以直接变成不可能**，不必依赖 Agent 自律。处理方法见 P0-8。

## 2. 根因：不是设计错了，是**层次串了**

甲乙两案其实各自说对了一半，把它们合起来才是完整结论。

**甲案说对的是**：分区目录 = git 分支的弱化手搓版。分区是**传输层**，而 git 已经提供了传输层（分支=物理隔离、worktree=独立工作目录+独立 index、PR=待审队列+讨论区、merge=入库、revert=回滚）。在手搓的传输层上继续叠机制，是往错的方向加码。

**乙案说对的是**：`flow` 在**模仿** git 做版本管理（`supersedes` 取代、整品类复检+自动回滚），而且做的是更弱的一版。但 flow 里另有一半**不是**版本管理，而是**数据准入语义**——6 个审核标注字段、`verify_status` 枚举白名单、schema 一致性、异常值阈值、去重口径。这些是本站特有的，git 不提供，**必须自己留着**。

**根因一句话**：这套架构把 git 当**消息队列**在用（分区文件既是私有工作区又是共享交接物，见乙案 2.3），同时让 `flow` 去承担**版本管理**，结果两层都不干净。

**修正方向**：**换掉传输层，留下语义层**，而不是二选一地"全盘 git 化"或"继续自研"。

| 职能 | 现状 | 目标 |
| --- | --- | --- |
| 传输 / 隔离 | 手搓分区 + 共享 index + 单工作树 | git worktree + 分支（原生） |
| 版本 / 冲突 / 回滚 | 手搓（`supersedes` + 整品类自动回滚） | git（merge / revert） |
| 准入语义 | 自研 flow 关口 | 自研 flow 关口（**保留**） |
| 议题 / 任务队列 | 无（只存在于对话与提交信息） | GitHub Issues（原生） |

**统一裁决原则**（建议两方都用它来检验本方案）：

> 凡是 **git / GitHub 原生已有**的（隔离、合并、回滚、评审门、议题、任务队列），一律不重造；
> 凡是属于**本仓库数据质量语义**的（来源优先级、审核标注字段、异常阈值、关口校验、订正稿替换），保留在自研工具里。
>
> 推论：`flow.mjs` 的**关口校验**留，`flow.mjs` 的**传输与版本职能**退场；乙案方案 E 里 `flow:lock` / `flow:issue` 属于"重造原生能力" → 否决；`flow:review`（谁 review 了什么）有语义价值 → 但它不需要新命令，**改成 journal 里多一个 `verdict` 字段**即可（P0-3 顺带做掉）。

## 3. 目标架构

**角色与位置**

| 角色 | 工作位置 | 动作 | 硬边界 |
| --- | --- | --- | --- |
| 采集方 A ×N | worktree `../wt-collect-<任务号>`，分支 `collect/<任务号>-<品类>` | 分区流程 → `flow:submit` → 推分支 → 开 PR | 只开 PR；不碰 main；不碰他人 worktree |
| 修正方 B ×N | worktree `../wt-review`，分支 `review/<批次号>` | 读 PR → `flow:claim` → 核对/订正 → `flow:publish` → 推分支 → 请用户合并 | 一个 PR 一个负责人 |
| UI 开发 | worktree `../wt-feat-<主题>`，分支 `feat/<主题>` | 改 `src/**` → PR | 与数据 PR 无文件交集 |
| 用户 | GitHub 网页 | 看板、**批准 merge**、裁决冲突与口径、定剔除 | merge 权只在用户 |

**关键语义变化**：**PR 被合并 = 原来的"上线时刻"**。合并前站点展示的是上一个已发布版本，这是本方案对现有语义最大的一处改动（见 5.1）。

**四层各司其职**（对齐乙案第 7 节结语，但划清边界）

```
git     管「谁改了什么、能否合并、能否回退」       → 分支 / worktree / PR / merge
flow    管「数据是否达到可入库标准」              → 关口校验 + 订正稿替换 + 归属推进
journal 管「谁在什么时候把什么推进了一步」         → append-only 事实（merge=union）
Issues  管「有什么疑问待解、下一件做什么」         → 原生，不自研
（locks 不在这一层：分支隔离后没有需要互斥的场景，乐观锁仅作兜底）
```

## 4. 分阶段实施清单

排期原则：**P0 与 P1 不依赖任何外部条件**（不依赖 gh、不依赖平台多 cwd），先在两个 Agent 现有习惯下把**会丢数据/会互相踩**的问题消灭掉；P2 才引入新工作方式。

### P0 — 止血（零习惯变更，改动集中在 `scripts/`）

| 项 | 做什么 | 依据 | 验收 |
| --- | --- | --- | --- |
| P0-1 | `writeLibrary` 加**内容指纹守卫**：载入库时记 `sha256`，写前重算，不一致即拒绝并提示"库已被他人修改，重新载入后重试" | 乙案故障 1 / 方案 A | 两个进程并发 publish 同一品类，后者报错退出，不静默丢数据 |

## 5. 语义变更与风险（这一节请两方重点挑刺）

新机制的收益大多来自**语义变化**，而这些变化必须双方明确接受，否则会在切换后变成"怎么和说好的不一样"。

### 5.1 `recall` 不再立即下架站点（最重要的变化）

现协议里 `recall` 会把产品从 `products.json` 摘掉，**站点立刻不再展示它**，理由是"物理冻结"。分支模型下这条不成立也不必要：召回发生在 B 的分支上，main 上的 `products.json` 没被动过，**站点会一直展示上一个已发布版本，直到 PR 被合并**。

- **好处**：访客不会看到产品凭空消失；"代表建中的品类长期挂在修正区"这个顾虑也消失（乙案/AGENTS.md 都提过）。
- **代价**：修正**错误数据**的时效性下降——发现线上某参数写错，要等 PR 合并才生效。
- **兜底**：保留 AGENTS.md「紧急修改」通道，但形态变了：`recall → 改 → publish → 推单产品分支 → 用户合并`，仍然只有几步，且 diff 只有一行。

### 5.2 `publish` 的"整品类复检 + 自动回滚"要改

乙案 2.2 的诊断成立：A 的 publish 触发了品类复检，因 B 的半成品不合规而失败，**A 的正确修改被回滚，报错还指向 B 的数据**。但结论不是删掉它（甲案也未主张删），而是：

- **P0 阶段**：复检范围从"整个品类"缩小为"本批涉及的产品 + 全库扫一遍只为报告，不再触发本批回滚"。理由：回滚的正确对象只能是**本批自己写坏的东西**，不能是别人早先就写坏的东西。
- **P2 之后**：全库一致性由 PR 的 CI 承担（main 永远校验通过 → 库里永远合法 → 复检几乎不可能失败），这条逻辑自然退化为廉价保险。

### 5.3 半成品（`_draft`）不再入库

代价：换个会话/换台机器接手 A 的在途草稿会看不到。考虑到草稿按定义就是"只有 A 写、A 的半成品"，且实际使用里 A 是在同一个 worktree 连续作业，本方案认为代价可接受。**但这是乙案方案 D 的诉求，甲案主张保留——请两方确认这个折中。**

### 5.4 每个数据变更都要过 PR

对 B 的操作成本增加（多两次 push + 一次等用户合并）。缓解：B 的 PR 以**批次**为单位（一个品类的召回批 = 一个 PR），不是每款一个 PR。

### 5.5 平台并发上限 2 是硬参数

甲案第 8 节提的这条我认。它意味着：

- 任何"靠加大并发提升吞吐"的设计都不可行；**效率必须来自任务可切分、可断点续跑**（Issues 队列 + 批次 PR 正是为此）。
- P2-4 的 Issue 粒度定为**产品级 issue**（不做到字段级；字段写进正文）。乙案 Q5 的"字段级更精确但数据量大"——在 2 并发下，字段级 issue 的维护开销会吃掉收益。

### 5.6 隔离是软的：四条兜底（对应 1.4 约束 1）

用户已明确：可以为每个 Agent 指定不同工作目录，但**不强制**，仍有小概率在目录外读写。这意味着"分支隔离 = 结构性消灭互踩"这个论断要打个折。本方案的态度是：**不追求硬隔离（做不到），而是保证越界的代价小且可见**。

| # | 兜底 | 挡什么 / 挡不住什么 |
| --- | --- | --- |
| ① | **P0-8 统一根目录解析口径** | **把越界写入变成结构上不可能**（针对脚本路径）：脚本只按自身位置解析，跑哪个 worktree 的脚本就只能写哪个 worktree。这是四条里唯一"根治"性质的 |
| ② | **P0-1 的指纹守卫** | 挡"读进来之后、写回去之前，文件被别人改过"→ 这在同一文件被两个进程写时就是全部场景，**与目录无关**。挡不住"写错文件"（写到了另一份 products.json，那份文件本身没被动过） |
| ③ | **P0-7 的操作自证 + journal 记 `branch`** | 挡不住误写，但把"在 main 里跑采集分支的命令"从**静默**变成**当场可见、事后可查**。这是本项目一贯的思路：不靠纪律，靠可见性（journal 就是为此存在）。**它兜的是 ①② 挡不住的那部分：Agent 直接按绝对路径手改文件** |
| ④ | **P1-8 的会话纪律**（决定必须落仓库文件） | 挡"换了工作目录 → 客户端项目记忆另起一份 → Agent 失忆"。这是 worktree 模型下**最容易被忽略的副作用**：本机记忆目录按项目路径派生（`…/-d-GitHub-Pages-moyu929-github-io--p2-…`），换到 `D:\GitHub Pages\wt-xxx` 就是另一个键，历史决策读不到。对策是让仓库文件（AGENTS / HANDOFF / docs / issue）成为唯一权威记忆——这也是本仓库已有的做法 |

**另外一条不做的选择**：不为软隔离引入"每个 Agent 一个独立 clone"或"读写白名单/沙箱"。理由：clone 只是把共享 `.git` 换成共享磁盘，越界概率不降（绝对路径照样能写到别的 clone）；沙箱是平台能力，不在仓库控制范围内。**能自己控制的只有"越界之后损失多大、能不能查出来"，这就是上面①②③④四条。**

## 8. 请两方回复的格式建议

为便于汇总，请按下面结构回复（写到 `docs/proposals/评审意见_<角色>_YYYY-MM-DD.md`）：
