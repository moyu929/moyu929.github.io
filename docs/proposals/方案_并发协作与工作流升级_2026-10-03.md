### 0.5.3 乙评 §8 引发的诊断修正（1.6）

v1 把「故障 1」整体归因于**并发**。乙评给出的实测是：那次失败（`UNKNOWN: unknown error, open '...products.json'`）**发生在无并发的单 Agent 批量写场景**，成因是长时间批量写 + Windows 文件锁。

这改变了结论：**批量稳定性与并发安全是两个问题，前者更前置**（单 Agent 就会发生）。v1 的 P0 只覆盖后者。v2 补上前者：P0-4 断点续跑、P0-3 写库重试。

### 1.6 故障 1 的真实触发形态（乙评 §8，本轮最重要的诊断修正）

乙评实测：`flow:publish` 中途报 `UNKNOWN: unknown error, open 'D:\...\data\vacuum\products.json'`，**当时没有并发**，成因是长时间批量写 + Windows 文件锁。

含义：**「批量稳定性」比「并发安全」更前置**——单 Agent 批量 publish 517 条就会触发。v1 的 P0 只治并发，漏了这一类。v2 补 P0-3（写库重试）与 P0-4（幂等重跑）。

（附带事实：现有实现对"中途失败"其实是**可恢复**的——失败时产品文件未被删除，仍在 `_review`，重跑能接上；但重跑会对已成功的项报"修正区没有这个文件"并 `exit 1`，**用户无法凭输出判断状态**。P0-4 要把这个"事实可恢复"变成"显式可恢复"。）

## 2. 根因：不是设计错了，是**层次串了**

**甲案说对的是**：分区目录 = git 分支的弱化手搓版。分区是**传输层**，而 git 已提供传输层。

**乙案说对的是**：`flow` 在**模仿** git 做版本管理，且做的是更弱的一版。但 flow 里另有一半**不是**版本管理，而是**数据准入语义**（6 个审核标注字段、`verify_status` 白名单、schema 一致性、异常阈值、去重口径）——git 不提供，必须自己留着。

**根因一句话**：这套架构把 git 当**消息队列**用（分区文件既是私有工作区又是共享交接物），同时让 `flow` 去承担**版本管理**，两层都不干净。

**修正方向**：**换掉传输层，留下语义层**。

| 职能 | 现状 | 目标 |
| --- | --- | --- |
| 传输 / 隔离 | 手搓分区 + 共享 index + 单工作树 | git worktree + 分支 + PR（原生） |
| 版本 / 冲突 / 回滚 | 手搓（`supersedes` + 整品类自动回滚） | git（merge / revert） |
| 准入语义 | 自研 flow 关口 | 自研 flow 关口（**保留**） |
| 议题 / 任务队列 | 无 | GitHub Issues（原生） |

**统一裁决原则**：

> 凡是 **git / GitHub 原生已有**的（隔离、合并、回滚、评审门、议题、任务队列），一律不重造；
> 凡是属于**本仓库数据质量语义**的（来源优先级、审核标注字段、异常阈值、关口校验、订正稿替换），保留在自研工具里。
>
> 推论：`flow.mjs` 的**关口校验**留，**传输与版本职能**退场；乙案方案 E 的 `flow:lock` / `flow:issue` 否定；`flow:review` 落为 journal 的 `verdict` 字段。
> **本轮的补充**：`flow:status` 的**跨区可见性**保留并增强（P0-6）——它属于"可见性"而非"传输"，与上面不冲突。

## 3. 目标架构

### 3.1 角色与位置（按两方回答的 cwd 现实修正）

甲评 Q1 与乙评 Q1 的答案**不同**，且两者必须同时成立：

- **甲侧**：子 Agent 的 cwd 由编排方注入的提示词决定 → **可以固定到 worktree**。
- **乙侧**：会话每次从 `D:\GitHub Pages\moyu929.github.io` 启动，**没有其他 cwd** → **不能固定到 worktree**。

| 角色 | 工作位置 | 动作 | 硬边界 |
| --- | --- | --- | --- |
| 采集方 A ×N（编排方 spawn 的子 Agent） | worktree `../wt-collect-<任务号>`，分支 `collect/<任务号>-<品类>` | 分区流程 → `flow:submit` → 推分支 → 开 PR | 只开 PR；不碰 main；不碰他人 worktree；**编排方必须注入本 worktree 的绝对路径** |
| 修正方 B | **主目录**（`d:\GitHub Pages\moyu929.github.io`），可在此切分支 | `gh pr checkout <PR>` → `flow:claim` → 核对/订正 → `flow:publish` → 推回该分支 → 请用户合并 → `git switch main` | 一个 PR 一个负责人；**不得直推 main** |
| UI 开发 | worktree `../wt-feat-<主题>`，分支 `feat/<主题>` | 改 `src/**` → PR | 与数据 PR 无文件交集 |
| 用户 | GitHub 网页 | 看板、**批准 merge**、裁决冲突与口径、定剔除 | merge 权只在用户 |

★ **这条修正带来一个必须写死的约束**：**A 的输出必须通过 PR 到达 B**。若 worktree 先于 PR 上线，B 在主目录跑 `flow:status` 看到的是**主目录的 `_intake`（空）**，A 提交的东西 B 根本看不见 → **协作停摆**。这正是裁定 4 把 worktree 与 PR 合并为同一阶段的原因。

**关键语义变化**：**PR 被合并 = 原来的"上线时刻"**（合并前站点展示上一个已发布版本，见 5.1）。

### 3.2 四层各司其职

```
git      管「谁改了什么、能否合并、能否回退」   → 分支 / worktree / PR / merge
flow     管「数据是否达到可入库标准」+ 跨区可见性 → 关口校验 + 订正稿替换 + status
journal  管「谁在什么时候把什么推进了一步」      → append-only 事实（merge=union）
Issues   管「有什么疑问待解、下一件做什么」      → 原生，不自研
（locks 不在这一层：需要互斥的场景只剩"同一文件两个进程同时改"，由 P0-3 乐观处理）
```

## 5. 语义变更与风险

### 5.1 `recall` 不再立即下架站点

分支模型下召回发生在 B 的分支上，main 未被动过 → **站点一直展示上一个已发布版本，直到 PR 合并**。

- **好处**：访客不会看到产品凭空消失；"代表建中的品类长期挂在修正区"的顾虑消失。
- **代价**：修正**错误数据**的时效性下降。
- **兜底**：AGENTS.md「紧急修改」形态变为 `recall → 改 → publish → 推单产品分支 → 用户合并`，diff 只有一行。
- **注意**：`_review` 的**可见性**不受影响（它仍入库，见裁定 3）——即"这个产品正在被修"依然对所有人和用户可见。这一点乙评 §3.1 的论证成立，但它**反对的对象是 v1 并不存在的主张**。

### 5.2 `publish` 复检：区分"本批写坏"与"历史遗留"

见 P0-5。乙评 §4-① 的措辞修正已采纳：历史遗留问题**照样阻塞**（否则成了默认放行），但报错必须把责任归属讲清楚，避免"一堆没碰过的产品报错 → 全部忽略"。

### 5.3 半成品（`_draft`）不再入库

代价：草稿零备份。条件（甲评 §3.3）：**能过校验就 submit**——`_intake` 是 tracked，submit 即获得备份，`withdraw` 可随时撤回。把草稿的最长暴露窗口压到一个会话内。

> 更正乙评 §3.3：`withdraw` 不会失效（它是物理移动，与 git 跟踪无关）。

### 5.4 每个数据变更都要过 PR

对 B 的操作成本增加（切分支 + push + 等用户合并）。缓解：① PR 以**批次**为单位；② **PR 正文自动汇编**（P2-6），把"额外成本"变成"省掉 `docs/audit/` 一半手写工作"。

### 5.5 平台并发上限 2 是硬参数

- 任何"靠加大并发提升吞吐"的设计都不可行；效率必须来自**任务可切分、可断点续跑**（P0-4 + P2-6 正是为此）。
- Issue 粒度定为**产品级**（字段写进正文）。

### 5.6 隔离是软的：五条兜底

用户已明确隔离非强制；乙评又证明 **B 无法固定到 worktree**。本方案的态度是：**不追求硬隔离（做不到），而是保证越界的代价小且可见**。

| # | 兜底 | 挡什么 / 挡不住什么 |
| --- | --- | --- |
| ① | **P0-1 统一路径口径** | **把脚本层面的越界写入变成结构上不可能**（5 个脚本 / 18 处）。唯一有"根治"性质的 |
| ② | **P0-3 指纹守卫 + 写失败重试** | 挡"读进来后、写回去前文件被别人改过"（与目录无关）；挡不住"写错文件" |
| ③ | **P0-7 操作自证 + journal 记 `branch`** | 挡不住误写，但让"在 main 里跑采集分支命令"**当场可见、事后可查**。兜的正是 ①② 挡不住的那部分：**Agent 直接手改文件** |
| ④ | **P0-8 pre-commit 钩子** | 兜"顺手 `git add -A`"这个最高频事故（机制性，非纪律性） |
| ⑤ | **P2-4 编排方义务**（甲评 §4.1） | 兜**唯一被实测确认"已发生"**的越界向量：编排方提示词里写死主仓绝对路径 → 整批子 Agent 写回主树 |
| ⑥ | **P2-5 会话纪律** | 兜"换目录 → 客户端项目记忆另起一份 → Agent 失忆"：会话开始读 `AGENTS.md` + `HANDOFF.md` + `flow:status`；**任何需跨会话保留的决定必须写回仓库文件** |

**不做的选择**：不引入"每个 Agent 一个独立 clone"或读写沙箱。理由：clone 只是把共享 `.git` 换成共享磁盘，越界概率不降；沙箱是平台能力。**能自己控制的只有"越界后损失多大、能不能查出来"**。

### 5.7 新增风险：P2 阶段切换本身

P2 是在途清零后的一次性切换，若中途有人仍在旧模式工作（在主目录直接提交分区文件），会出现"一半人走分支、一半人走共享树"的混合态。对策：P2-6 的 `cutover` issue 必须在切换前挂出，双方在 issue 下确认齐备后再切换；P2-7 用一个小品类演练验证。

## 7. 本方案明确不做的事

| 不做 | 理由 |
| --- | --- |
| 自研议题/看板（ticket JSON + 状态机） | GitHub Issues 免费且人类可直接参与（双方一致） |
| `flow:lock` 之类的软/硬锁 | 需要互斥的场景只剩"同一文件两进程同时改"，由 P0-3 乐观处理；2 并发下加锁是纯开销 |
| **`flow:status --all-worktrees`**（乙评 §2 建议） | **驳回**：分支模型下 B 看 PR 即可；跨 worktree 遍历会把"看不见彼此"这个**已被 PR 解决**的问题重新引入。真实诉求由 P0-6 满足 |
| 把 worktree 与 PR 分两个阶段上线 | **驳回（v2 新增）**：B 无法固定 cwd，worktree 先上会断掉传输链（3.1） |
| 立刻重构"每产品一文件" | 一行一款已能按行合并；触发条件见 P3 |
| 回到快照锁看门 / 引入实时互斥 | 双方一致 |
| 自建 Agent 间消息通道 | PR/issue 评论区 + 会话开头 `gh issue list`/`gh pr list` 已覆盖 |
| 立刻做 schema 版本化 | 先用"schema 变更随数据 PR 但单独 commit + CI 全库校验"兜住 |
| 把 `flow.mjs` 整体删除 | 关口校验 + 跨区可见性是本站特有语义，git 不提供；只让传输/版本职能退场 |
| 为并发引入数据库 / 服务化 | 1MB 数据 2 个 Agent，`git` + 单文件足够 |
