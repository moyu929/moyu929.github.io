- **结论**：**接受撤除该 lint 规则。** 但反驳理由中有一处事实需要纠正，且这处纠正恰好指向一个更好的替代方案。

## 0. 一句话

开发方用 6 条在途数据证明「限定竞品后仍会误报」——**这个论证成立，我撤回恢复该规则的建议**。

但 §5.2 写的「型号取自官方规格页/API」与事实不符：这 6 条的 `verify_source` 是**太平洋电脑网**，
与库里另外 529 款竞品回填型号的来源**完全相同**。这个纠正很重要——它说明规则失败的根本原因
不是「来源不同」，而是**规则本身无法区分这两种情况**。

### 1.2 §5.2 的一处事实错误：来源不是官方

§5.2 写：

> 它们是甲这一轮新采集的竞品，**型号取自官方规格页/API**（比产品名权威）。

实测这 6 条：

```
aux_sdxpro_1p      verify_url = g.pconline.com.cn   verify_source = ['太平洋电脑网']
midea_ks2_15p       verify_url = g.pconline.com.cn   verify_source = ['太平洋电脑网']
tcl_q7max_xf_15p    verify_url = g.pconline.com.cn   verify_source = ['太平洋电脑网']
```

**全部来自太平洋电脑网**，不是官方。而 `change_log` 里说的「官方商城同系列商品页印证」是用来印证
**系列名**的（「省电侠Pro」「酷省电二代」），型号 `KFR-26GW/BpR3AES1(B1)` 本身取自太平洋规格表。

### 1.3 更关键的事实：全库竞品的来源是同一个

```
已入库竞品 618 款的 verify_source 分布：
  太平洋电脑网  617   ← 几乎全部
```

我回填的那 517 条型号，来源也是太平洋规格页的**页面标题**；
这 6 条的型号来自太平洋规格表的**「型号」字段**。

**两者来源完全相同。** 规则拿不到任何信号去区分它们：

| | 型号取自 | 与产品名的关系 | 规则判定 |
| --- | --- | --- | --- |
| 517 款（已入库） | 太平洋页面标题 | 恰好相同 | 通过 |
| 6 条（在途） | 太平洋「型号」栏 | 不同（营销名） | 误报 |

所以「规则把用了更好来源的当成可疑」这个解释**不成立**——来源一样，只是取自同一页面的不同位置。

**真正的失败原因是：规则建立在一个不可观测的假设上**——
「型号应当出现在产品名里」隐含「型号是从产品名提取的」，而实际库里有两种提取方式。

## 2. 我接受撤除，并撤回我的建议

§5.2 引用了我自己 §2.3 的退出条件（「若将来出现竞品用营销名的情况……不会挡路」），
说得对：**这个「将来」就是现在**。

我当时的推理链是：
1. 79 例误报全是小米系 → 竞品侧 0 例 → **规则不是无效，是作用域错了**
2. 但我只验证了**已入库的 518 条竞品**，而这个样本的选择性很强：
   它们恰好全是「我这一轮从产品名回填型号」的那批

**这是典型的「用自己造的样本验证自己造的规则」**。规则之所以 0 误报，
是因为我回填的型号本来就是从名字提取的——**规则和我的操作是同源的，所以它必然通过**。

这条推理的漏洞开发方抓住了。我撤回 §2.3 的建议。

## 3. 替代方案：不靠字符串规则，靠「来源标记」

规则不可用的根因是**信息缺失**——库里没有字段记录「这个型号是怎么来的」。

如果补上这个字段，判断就变得可靠：

```jsonc
{
  "model_code": "KFR-26GW/BpR3AES1(B1)",
  "model_code_source": "spec-table",   // 来自规格表「型号」栏
  // vs
  "model_code_source": "name",        // 从产品名提取（fill-model-codes.py）
}
```

有了它，lint 可以写成**精确**的规则：

```js
// 只在「型号来自产品名提取」时，型号理应出现在产品名里。
// 来自规格表型号栏的（来源比产品名权威）不适用此规则。
if (p.model_code_source === 'name' && !name.includes(p.model_code)) → 警告
```

这样：
- 517 款（`source: name`）→ 规则生效，能抓住「提取时截错了」这类真 bug
- 6 条（`source: spec-table`）→ 不适用，**0 误报**
- 「型号抄错」仍主要靠参数逐项比对（HANDOFF §0.3 的做法），规则不承担这个责任

**成本**：
- schema 加 1 个字段（40 个品类，可脚本批量）
- `fill-model-codes.py` 回写时标 `source: name`（那 517 条我有记录）
- 6 条在途数据由采集方标 `spec-table`
- lint 规则约 10 行

**我建议这个替代方案进 P3，不进 P2**。理由：
- 它解决的是「未来采集数据的质量」，不是「当前库的缺陷」
- 需要 schema 变更（按裁定 8，schema 变更要单独 PR）
- 当前 0 误报、0 漏报的现实下，不是阻塞项

**如果你认为不值得做，我不坚持。** 原规则撤除是对的——
在一个没有来源标记的库里，那条字符串规则做不到 net positive。
