## 1. 回答 6.2 的三个待确认

### 6.2-① `flow:claim` 的可见化是否覆盖我 §3.1 的风险

**是，覆盖了。** 我 §3.1 描述的场景是：claim 555 个键时混进了别人的 38 条，我**靠 `change_log` 字符串匹配**才区分出来。

P0-6 的 ①（打印每个键的 submit actor + 时间）与 ②（journal 记 `submitActor`）正好提供这个信息，
而且比我的字符串匹配**更可靠**（结构化字段，不依赖 `change_log` 文案）。

**但我要追加一条实测发现，P0-6 需要一并覆盖**：

我这轮的实际操作是 `cd data/_draft && ls */*.json` 生成 key 列表，然后
`node scripts/flow.mjs claim $KEYS`。**这个 `ls` 是我自己写的临时命令，不在任何工具里**——
也就是说「批量 claim 时如何拿到 key 列表」这件事，工具链没有提供入口。

结果是我只能靠 `change_log` 反查。**建议 P0-6 ⑥**：
`flow:claim` 支持不带 key、只按 actor 或分区批量操作（如 `flow:claim --from collect-wash --zone intake`），
让「认领某人提交的」成为一等操作，而不是手工拼 key 列表。

### 6.2-② pre-commit 钩子会打断既有「随做随提交」纪律

**会打断，我确认这是真问题**，并且方案给的修法（提交信息带 `flow:` 前缀）**我同意**。

补充一条实测：`git log --format="%s" -50 | grep -c "^data:"` = **19**，
即近 50 个提交里 19 个用 `data:` 前缀，**0 个含 `flow:`**。

所以钩子上线后，第一次执行「分区流转随做随提交」就会被拒。这不是小摩擦——
`AGENTS.md` §5 明确要求「流转动作随做随提交」，钩子与文档纪律直接冲突。

**建议**：
1. 提交信息前缀从 `data:` 扩展为 `data(flow):` 或 `flow:`，并**同步修改 `AGENTS.md` §5**；
2. 钩子的判定放宽为：**提交信息含 `flow` 字样即放行**（不严格要求前缀位置），
   避免格式微调就触发拒绝。

### 6.2-③ P1-2 格式转换的时点

**我的判断：不需要 drain 全部在途品类，但必须避开「B 正在 publish 某个品类」的瞬间。**

理由：

- P1-2 是**一次性脚本 + git commit**，转换前后内容语义完全等价（只是换排版），
  不涉及数据变更。转换后 `products.json` 里那款产品**照样在**，`_review` 的文件也不受影响。
- 真正的风险只有一个：**B 正在 publish 时，转换脚本重写同一个 `products.json`**。
  这会被 P0-3 的指纹守卫挡住（转换脚本也算一个写入者），但守卫是**拒绝**不是**排队**——
  B 的 publish 会失败，需要重跑。

**结论**：转换放在 P1-1（写入规范落地）完成之后、**且当前无 publish 进行中**的窗口执行即可。
不需要 drain 6 个品类。执行前跑一次 `flow:status`，确认 `_review` 数量未变即可作为判据。

## 2. 开工前必须补的一件事（方案未覆盖）

我在核实过程中实测发现：**`flow.mjs` 的分区操作只删文件、不删目录**。

```
$ find data/_intake data/_review -type d -empty | wc -l
42
```

我这一轮 publish 了 517 条，`fs.rmSync(src)` 把文件删了，但 `data/_intake/<23个品类>/`、
`data/_review/<23个品类>/` 这些**空目录全部留下**。`.gitignore` 不跟踪空目录，所以 git 里看不到，
但它们：

1. 让 `flow:status` 的输出变得嘈杂（我第一次统计时误以为 23 个品类都有在途数据）；
2. 会误导另一个 Agent 判断「这个品类有在途数据」；
3. P1-4 把 `_draft` 移出 git 后，这类残留目录更容易堆积。

**建议 P0 补一项 P0-10**：分区操作后清理空目录（`pruneEmptyDirs(zone)`），
并在 `flow:status` 里对空品类不输出条目。

这项成本约 15 行，与 P0 其他项同一批做掉更划算。

## 4. 对 v2 的总体评价

**v2 修正了 v1 的两处真错误，且都修得比我提的更准：**

| v1 的错误 | v2 的修正 |
| --- | --- |
| P0-2 要求 `claim --by` == submit actor | v2 承认这会**瘫痪正常交接**（submitter 是 A、claimer 是 B，必然不同），重写为「打印来源 + 自采自审警告」 |

第 1 条是**我的责任**——我在乙案里提「`claim` 加 owner 校验」，方案作者把它实现成硬拦，
结果我的诉求（防越量认领）被误解成「禁止 A 提交 B 认领」。v2 的 `selfReview: true` 警告方案是对的。

第 2 条我也没想到：我提「worktree + git 分支」时假设**所有 Agent 都能切到 worktree**，
但我自己的会话每次都从主目录启动。方案采纳我的实测后重排了阶段，逻辑成立。

**我撤回了乙案 §3 的反对**（方案指出我是误读——v1 裁定 3 本来就是「只把 `_draft` 移出 git」，
我的论证与方案结论一致，`docs/flow/recalls/` 补偿机制不需要建立）。

**我保留 §5.2 的一个判断**：P1-1 与 P1-2 必须同时（方案已采纳并颠倒顺序，我同意），
但 P1-3 行级替换降为可选，方案给的理由是「规范化序列化器让整文件重写的 diff 与行级替换等价」——
这个理由成立，我接受。
