## 2. 必须补的：写规范第三要素「写入记 journal」未实现

方案 v2 §4 的 P1-1 定义写规范三要素：① 一行一款序列化 ✅ ② 写前指纹守卫 ✅ ③ **写入记 journal ❌**。

实测：`classify-facets.py` / `shrink-images.py` / `import-brands.py` / `fill-*.py` / `mi-store.mjs` / `miot-spec.mjs` 六条批量写路径**写库后均不产生任何 journal 条目**（两侧库实现都没有留痕接口，各脚本也没自行追加）。后果：B 用批量工具重写整品类（如 classify-facets 的 517 条级作业）后，`flow:log` 对这次改动**零记录**——journal 作为「跨方共享事实流」出现盲区，只能靠 git log 兜底。这正是方案要消灭的「可见性缺口」的一种复发形式。

**建议修法**：留痕做进两个库实现本身——`saveLibrary()/library_io.save()` 增加可选 `actor` 参数，写入成功后向 `data/_flow/journal.jsonl` 追加一条 `{ts, actor, action:'batch-write', key:'<品类>/products.json', count}` 级别的粗粒度条目（批量写一条即可，不必逐产品）；六条路径各自传入自己的 actor 名。工作量小，且 selftest 补一条断言。

## 3. 必须修的：AGENTS.md 的「唯一写库者」表述已与实现漂移

`AGENTS.md` 角色表 B 行与 §3.1 分区表仍写「`products.json` **仅经 `flow:publish`** 写入」。P1-1 落地后的现实是：**批量工具（mi:apply、img:webp、miot:match --apply、classify-facets 等）经 `library_io` 直接写库**，这是合法且被守卫保护的路径。原表述会让下一个读规范的 Agent 误判这些工具违规（或反过来，误以为自己可以手改）。

**建议修法**：表述改为两层——「库写入**一律经 `library-io.mjs`/`library_io.py`**（规范序列化 + 写前指纹 + 留痕）；产品级生命周期操作（提交/认领/召回/入库）走 `flow:*`；批量工具经同一规范直写」。§5 提交纪律补一句「批量工具写库的提交信息同样需含 `flow` 标记（钩子会拦）」。这正是我们花了三轮文档要消灭的「工具与文档不一致」类问题，不要在收尾时又留一处。

## 4. 建议项：CI 的 Python 依赖钉死

`ci.yml` 在 ubuntu-latest 上跑 `npm run selftest`，而 selftest 用 `execFileSync('python', …)` 调 Python 侧序列化器。runner 镜像对 `python` 别名（vs `python3`）不作保证，且 selftest 至今**没有在真实 CI 上跑过**（还没有过 PR）——这是整条 CI 里唯一未验证的环节。建议：ci.yml 加 `actions/setup-python@v5`（钉 3.11+），或 selftest 里做 `python3` 回退。一行成本，消除镜像漂移风险。
