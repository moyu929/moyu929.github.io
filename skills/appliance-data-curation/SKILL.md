# 家电数据收录规范

本仓库是「家电参数横评」静态站：数据全部手写在 `data/` 下的 JSON，推送到 `main` 由 GitHub Actions 构建发布。本 skill 规范**如何采集、核验、录入**数据，保证各品类字段一致、来源可信、可复核。

## 何时使用

- 新增一个家电品类（如空调、洗衣机、冰箱、扫地机器人……）
- 修改/补充/订正某个品类已有产品的参数
- 判定某型号是否属于「国内在售」、是否为海外版
- 校核数据来源是否合规、是否需要标注额定/实测

## 数据模型与文件约定

```
data/categories.json                 品类清单（首页入口）
data/<category-id>/
  ├─ schema.json                     字段定义：显示位置、单位、能否排序
  └─ products.json                   已入库区：产品数据（线上站点唯一数据源，只经 flow:publish 写入）
public/images/<category-id>/         产品图，文件名 = 产品 id（不随分区流转）
```

```
data/_draft/<品类>/<id>.json         草稿区：收录中的半成品（采集方 A 的工作台，只有 A 写）
data/_intake/<品类>/<id>.json        待入库区：收录完成、等待审核方认领的交接队列
data/_review/<品类>/<id>.json        修正区：审核修正中的数据（审核方 B 的工作台，只有 B 写）
data/_flow/journal.jsonl             流转日志：谁在何时把哪个产品搬到了哪个区（append-only）
data/_sources/                       溯源与工具清单（入库，供复核）
  ├─ provenance.json                 逐条溯源：某产品的数据来自哪些来源、核验于何时
  ├─ patches/*.json                  参数补丁留档（内含 _来源）
  ├─ images.json                     产品图下载清单（品类/产品id → 图片URL）
  └─ pconline-targets.json           第三方规格页抓取清单
data/_locks/                         审核快照锁（已降级为结构冻结工具，见 AGENTS.md）
docs/audit/                          审核报告归档
skills/                              技能定义（客户端无关；各客户端目录只放指针）
```

- `category-id`、产品 `id` 只用字母数字和 `._-`，`id` 同时是图片文件名和分区文件名。
- **产品数据的生命周期**：收录写 `data/_draft/` → `npm run flow:submit` 进待入库区 → 审核方 `flow:claim` 认领到修正区 → 核验修正后 `flow:publish` 入库。规则与命令见 `AGENTS.md`「分区流转协议」。
- 新增品类三步：① 建 `data/<id>/schema.json`（可复制已有品类改；此时可以还没有 products.json，validate 对这种未登记目录只提示）② 建 `public/images/<id>/` ③ 首批产品 `flow:submit` 的同一提交里在 `data/categories.json` 追加一行。
- 卡片、对比表、筛选排序全部由 schema 驱动，**不需要写任何 Vue 代码**。
- 动手前先跑 `npm run flow:status` 看清各区现状；**已入库区任何人都不可直接手改**（原因与流程见 `AGENTS.md`）。

### schema.json 关键结构

- `groupBy`：**主分组固定为 `brand`（品牌）**。`order` 决定品牌顺序，`colors` 给徽章配色。产品的品牌值必须落在 `order` 里，否则不显示。
- `facets[]`：**可选的副分组维度**，结构与 `groupBy` 相同。品类自身的细分维度（`tier` 档位、`type` 类型、`series` 系列等）放这里，在界面上渲染成品牌下拉之后的额外下拉。**不要把品牌以外的维度放进 `groupBy`。**
- `searchFields`：参与搜索的字段 key，应含 `name` 与 `brand`。
- `primaryMetric`：主指标（一般 `official_price`），用于排序/统计。
- `fields[]`：每项含
  - `key` 对应 products.json 的键名；`label` 界面中文名；`type`（`text`/`number`/`tags`）；`unit`/`prefix` 单位与前缀
  - `card`：`title` 标题 / `chip` 价格胶囊 / `grid` 参数网格 / `tag` 底部标签；省略则只进对比表
  - `compare` 进对比表、`sortable` 出排序按钮、`stat` 参与顶部统计
  - `tagVariant`（`green`/`red`/`blue`）、`tagPrefix`（tags 类型配色与前缀）

### 通用字段建议

各品类至少保留这些通用字段，便于横向一致：`name`(型号)、`brand`(品牌)、细分维度(`tier`/`type`/`series`)、`official_price`(官方价)、`second_hand`(二手价)、`pros`/`cons`/`tags`、`img`、`year`、可选 `month`。再按品类补充核心参数与决策字段。

## 收录范围

本站是**多品牌横评**，小米/米家与其他品牌**同等收录、同等展示**：

- **主收录**：小米/米家自有品牌 + 主流家电品牌（美的、海尔、格力、戴森、追觅、石头、科沃斯、云鲸、添可、松下、苏泊尔、九阳、飞利浦、西门子、老板、海信、TCL 等）的中国大陆在售或发布型号。
- **同等地位**：任何品牌都不作为「小米的竞品」呈现。分组维度是**品牌**，不是「小米 vs 竞品」。品类简介、选购建议、文案里不要出现把其他品牌称作竞品的说法。
- 不含：海外版/港台版、白牌/生态链非主流品牌（除非用户明确要求）。
- 每款产品必须有 `brand` 字段。小米/米家系产品（产品名以「米家」「小米」「Xiaomi」开头）统一填 `小米`。
- **`brand` 按零售商品名牌归类，不按代工/协议厂商划分**：`miot_model` 的厂商前缀（zhimi 智米、dmaker  Dreame、chunmi 纯米、
  fengmi 峰米、leshow 鹿秀、deerma 德玛、loock、lumi、viomi 云米、yeelink 等）只说明该型号由生态链企业代工，
  但零售时挂的是「米家/小米」品牌，因此 `brand` 仍填 `小米`。协议厂商前缀只作溯源线索，不改品牌归属。
- 同一硬件不同固件改版（如「降本」「更换 MCU」）视为**同一型号**，只保留一条，不要按改版拆条。
- 同一商品名称/系列跨年份有实质性迭代（型号代码、核心性能、能效、结构或关键功能变化）时，视为不同版本并分别收录；`name` 必须带版本后缀，优先用具体年份（如「巨省电 1.5匹（2024款）」/「巨省电 1.5匹（2026款）」），年份不可核实时用「新款」「旧款」并在来源核实后尽量补齐年份。不得仅因促销、颜色、固件或无关紧要的物料变更而拆分。

## 信息来源与优先级

按可信度从高到低，**冲突时以高优先级为准**：

1. **官方（权威）**
   - 小米商城 `m.mi.com` / `www.mi.com/shop`、小米官网规格页、小米有品、米家 App 接入页
   - 其他品牌同理：品牌官方商城、官网规格页、官方说明书 PDF
   - 官方**说明书 PDF**（最权威的铭牌参数：CADR/功率/尺寸/重量等额定值）
2. **权威第三方（补充）**
   - 中关村在线 ZOL、太平洋电脑网、苏宁自营、京东自营商品页
   - 用于官方未公开字段的补齐；同一数值需**至少两处相互印证**
   - ZOL 参数页（`detail.zol.com.cn/<目录>/index<ID>.shtml` 的 param 页）有「产品类别」栏，
     在太平洋不给分类字段时能顶上；两者可交叉印证，也可互为补漏
3. **一般媒体（仅作印证，不得单独定值）**
   - 科技媒体、评测与拆机文、导购文、聚合内容，**含 AI 生成内容**
   - ⚠️ 这类内容大量互相抄袭、甚至由 AI 拼装，**「多家都这么说」常常是同一个源头**，
     因此**转载/同源不算多源印证**；看到具体数值先找它的原始出处。
   - ✅ 允许的两种用法：
     1. **印证**已在官方或权威第三方取到的值——一致则提高置信度，矛盾则触发复核；
     2. 官方与权威第三方都拿不到、且该参数**不涉及安全 / 电气额定 / 医疗健康**等关键项时，
        若**至少两家彼此独立**的媒体一致，可作为补充值录入，`verify_status` 不得高于「已核验（多源）」。
   - ❌ **不允许**：仅凭一条媒体信息就给产品定下参数值，哪怕它写得非常具体、非常像官方口径。
   - 📝 标注要求：`verify_source` 写媒体名（如「什么值得买」「IT之家」），
     `change_log` 写明「媒体印证：A、B 一致」或「媒体线索，待官方核实」，
     链接登记进 `data/_sources/provenance.json`；AI 生成内容必须标注「AI 聚合，仅作线索」。
4. **仅作交叉印证（不作准绳）**
   - `home.miot-spec.com` 等型号库：可用来核对**型号是否存在、型号代码、是否海外版、传感器/滤芯/电机等固件能力项**；其标注日期是固件协议收录/认证日期，**不等于上市时间**；该站存在大量固件改版重复条目，且收录并不完整，**不能以其缺失否定某型号存在**。

## 审核标注字段（每款产品必带）

每条产品记录都要带 6 个「审核标注」字段，用来回答「这条数据凭什么可信、什么时候核的、改过什么」。
新增品类时要把这 6 个字段加进 schema，新增产品时要把 6 个字段都填上：

| 字段 | 含义 | 取值 |
| --- | --- | --- |
| `verify_status` | 核查状态 | `已核验（多源）` / `已核验（官方商城）` / `已核验（第三方）` / `待核验` |
| `verify_date` | 核查时间 | `YYYY-MM-DD`，未核验写 `—` |
| `verify_source` | 信息来源 | 标签数组，如 `["小米商城","太平洋电脑网"]`；未核验写 `[]` |
| `verify_url` | 来源链接 | 首选来源 URL；无则 `查不到` |
| `change_log` | 修改记录 | 本次改了什么、依据什么，如「2026-10-01 按商城在售目录核对名称/价格」 |
| `updated_at` | 最近更新 | `YYYY-MM-DD` |

**状态判定必须可追溯，不许手填**：

- `已核验（多源）`：至少两个独立来源印证。来源要能落到 `data/_sources/provenance.json`
  （逐条溯源：来源 + 链接 + 备注）或 `data/_sources/patches/*.json` 的 `_来源` 里。
- `已核验（官方商城）`：名称 / 价格 / 图片取自品牌官方在售目录（`data/_cache/search-*.json`、`product-*.json`），
  但没有第二个来源佐证参数。
- `已核验（第三方）`：参数来自**单一权威第三方规格站**（ZOL、太平洋等），且已按下方「第三方来源工具」的
  异常阈值逐字段过滤过。这是多品牌横评下的**正常状态** —— 非小米品牌往往没有可抓取的官方规格页，
  以权威第三方为唯一来源是这一类产品的实际状况，不应为了「凑官方来源」而降级或编造链接。
  但每个参数值仍须通过字段白名单与异常阈值校验，通不过的写 `查不到`。
- `待核验`：早期录入、找不到可追溯来源。**这是默认状态，不确定就不要往上标。**

改动数据时同步维护：改了什么就写进 `change_log`，重新核了就更新 `verify_date`，
新增来源就追加到 `verify_source`，并把新来源登记进 `provenance.json`。

`flow:submit` 与 `flow:publish` 会**强制校验**这 6 个字段是否存在、`verify_status` 是否取规范值，
缺字段的数据提交不出去、也入不了库。

## 核心规则（务必遵守）

1. **禁止编造与估算**：任何数值都必须可溯源到具体链接/报告；查不到就明确写「查不到」（或 `"—"`），绝不用推测值填充。
   媒体上的数值同样要能给出链接，并遵守「来源与优先级」第 3 条的层级限制（媒体只能印证，不能单独定值）。
2. **额定 vs 实测双口径**：官方国内页多为「额定值」，海外页/宣传页常用「实测值/测试值」。同一型号若两者都存在，拆成两列分别标注（如 `颗粒物CADR(额定)` / `颗粒物CADR(实测)`），不可混用。
3. **口径统一**：同一品类内统一采用同一口径基准（默认大陆官方额定口径），并在数据中标注来源性质。
4. **去重**：先按「型号代码」再按名称判重；命名陷阱（同名不同代、同代码跨区换名）要按型号代码核对，不能只看名字。
5. **海外版甄别**：仅在大陆官方渠道检索不到、且能确认主要面向海外/港台的，判为海外版并排除。
6. **数值型字段**：schema 声明为 `number` 的字段请填数字；确实无值的旧型号填 `"—"`（校验脚本会提示「排序时沉底」，属已知提示）。
7. **图片**：暂无产品图时 `img` 填 `null`（校验脚本会提示「暂无产品图」，属已知提示）；有图则文件名 = 产品 id。
8. **不碰已入库区，不越分区**：线上数据（`products.json`）任何人都不可直接手改——审核方修旧数据走
   `flow:recall → 修正 → flow:publish`；采集方发现库内数据有误，复制到草稿区改好后 `flow:submit`
   （工具自动识别为订正稿）。确有紧急情况见 `AGENTS.md`「紧急修改」。
9. **第三方的坑要防**：第三方站有系统性字段错标（详见下文「第三方来源工具」），
   对可疑数值采取「宁缺勿错」——**留空，不猜测、不换算、不补零**。

## 收录步骤（推荐流程）

1. **建品类骨架**：在 `data/categories.json` 加条目，复制一个已有品类目录改 schema：定 `groupBy`/`order`、`searchFields`、`primaryMetric`、`fields[]`。新品类收录期间可以只有 schema 没有 products.json（validate 只提示）。
2. **枚举候选型号**：从官方商城/官网列全该品类国内在售与经典型号；借助参考站核对型号代码与海外版。
3. **逐型号取证**：优先官方规格页/说明书 PDF；官方缺口再找权威第三方，要求双源印证。
4. **判定与去重**：剔除海外版、合并固件改版、确认命名歧义。
5. **写入草稿区**：每款产品一个文件 `data/_draft/<品类>/<id>.json`，字段照 schema，缺失写「查不到」，额定/实测分开标。半成品随便放，**只有 flow:submit 校验通过才会进入待审核队列**。
6. **提交待审**：`npm run flow:submit -- <品类>/<id>...`（校验 schema 合法性 + 6 个审核标注字段），然后按仓库纪律当场提交。
7. **（可选）本地预览**：`npm run build` 后 `npm run preview` 检查渲染。入库展示由审核方 `flow:publish` 完成，采集方不用管。

## 采集流水线（已固化到 scripts/）

步骤 2「枚举候选型号」与步骤 3「逐型号取证」可交由 `scripts/mi-store.mjs` 完成，**不要手抄网页**：

| 命令 | 作用 | 依赖 |
| --- | --- | --- |
| `npm run mi:enumerate -- <关键词...>` | 打开小米商城搜索页，抽取在售商品的名称/价格/官方图/商品ID，缓存到 `data/_cache/search-<关键词>.json` | Playwright（Node） |
| `python scripts/mi-store-enumerate.py <关键词...>` | 同上；本机只装了 Python 版 Playwright 时用这个（两者缓存格式一致，可互换） | Playwright（Python） |
| `npm run mi:detail -- <productId...>` | 拉官方商品详情（名称、现价、划线价、官方图、卖点文案），**纯 HTTP** | 无 |
| `npm run mi:specs -- <规格页URL...>` | 抓官方规格页并解析成 `{参数名: 值}`，**纯 HTTP** | 无 |
| `npm run mi:images` | 按 `data/_sources/images.json` 下载官方**原图**到 `data/_cache/img-raw/`（不入库） | 无 |
| `npm run img:webp` | 把原图转成 **≤320px WebP** 写入 `public/images/` 并回写 `img` 字段 | Python + Pillow |
| `npm run mi:apply -- <patch.json>` | 把字段补丁按 `品类/产品id` 精确定位写入 `products.json` | 无 |
| `npm run miot:crawl` | 按品类整库抓取 `home.miot-spec.com`（分页/并发 4/增量缓存到 `data/_cache/miot-*.json`，日志 `miot-crawl.log`） | 无 |
| `npm run miot:search -- <关键词...>` | 只抓该站首页结果，快速看型号 | 无 |
| `npm run miot:match [-- --apply]` | 用本地索引按官方名精确匹配，补 `miot_model` | 无 |
| `npm run pconline:specs` | 按 `data/_sources/pconline-targets.json` 抓第三方规格表到 `data/_cache/pconline-*.json` | Python 3 |
| `npm run flow:submit/claim/recall/publish/...` | 分区流转：收录完成提交待审、认领、召回复审、入库（见 `AGENTS.md`） | 无 |
| `npm run audit:snapshot/check/status/release` | 审核快照锁，已降级为结构冻结工具（schema 大改/发版验收前用，见 `AGENTS.md`） | 无 |

要点：

- **枚举必须按容器限定**：商城搜索页里顶部导航/推荐位同样是 `a[href*=product_id]`，只取 `.goods-list .goods-item`，否则会混入手机、平板等无关商品。
- **规格页是否可用要先探**：`www.mi.com/<slug>/specs` 这类老页多数是服务端渲染的（能解析到参数）；电视/投影等新页是前端渲染的，解析结果为 0 项，需改用其他来源。
- **回写必须锚定对象边界**：`mi:apply` 会校验「id 与目标字段之间不得再出现 `"id"`」，越界直接报错；不要用「从 id 向后找第一个 `"img": null`」这类正则，目标本身已有图时会写到下一个产品上。
- **补丁文件留档**：每次写入的 `patch.json` 放进 `data/_sources/patches/`，文件内用 `_来源` 记录每条数据的出处，便于后续复核。
- **图片**：站上统一存 **≤320px WebP**（文件名 = 产品 id，`img` 字段就是它）。
  尺寸依据是最大展示位 96×112 CSS px × DPR 3；原图先落 `data/_cache/img-raw/`，用 `npm run img:webp` 转换入库。

## 第三方来源工具与已知坑

### `home.miot-spec.com`（型号库，仅作交叉印证）

- 页面是 Inertia 应用，数据在 `<script data-page="app" type="application/json">{…}</script>` 里，
  解析要按 **JSON 括号配平**（别用宽松正则，会先抓到 `id="app"` 这个属性）。
- 检索入口 `https://home.miot-spec.com/s/<关键词>`，翻页 `?page=N`，每页 50 条；
  字段里有 `model`（协议型号）、`name`（官方中文名）、`attrs.icon_real`（官方图）、`attrs.verified_time`（协议认证时间）。
- **单次请求约 3.5 秒**，串行抓几百条会被误判为「卡死」；必须并发 + 增量落盘 + 日志（`data/_cache/miot-crawl.log`）。
  实测**没有反爬**：连续请求全部 HTTP 200，慢是站点本身慢。
- 官方图只有 **168×168 缩略图**，不足以作产品图（站内缩略图位 96×112 @2x），补图仍走官方商城主图。
- 红线：`miot_model`（如 `xiaomi.waterpuri.lx31`）与零售型号代码（如 `MR1692`）**不是一回事**，
  必须写进独立字段 `miot_model`，**禁止写进 `model_code`**；其认证时间**不是上市时间**；
  该站收录不完整，**缺失不能作为「型号不存在」的依据**。

### 太平洋产品报价（结构化规格表，补充来源）

- 小米商城商品页的参数表由 JS 动态加载，纯 HTTP 抓不到（渲染后正文仅千余字、没有规格区）；
  而太平洋的 `_detail.html` 是服务端渲染的表格，可作第二来源。
- 型号索引：`https://g.pconline.com.cn/product/<品类目录>/mijia/`（如 `cleaning_machine`、`yuba`），
  条目链接是 `<id>.html`，规格页是 `<id>_detail.html`。
- **已知系统性错标，必须过滤、不要照抄**：
  - 功率标签错位：把风暖功率标成「灯暖功率」，或把 `2800W` 写成 `28W`
  - 容量单位错：把 `L` 写成 `ml`（净水箱 `1ml`、污水箱 `0.7ml`）
  - 重量缺位：`约.6kg`
  - 型号栏塞产品名（型号写「3 Max」而不是型号代码）
  - 真空度单位混用：`18Kpa` / `26000毫巴` / 缺零的 `1800毫巴`
  - 家用品类里混入**工业机**（`产品类别=工业除湿机`），与本站按家用参数分档的维度对不上
- **同一事物的不同叫法**（写映射表时要把同义写法都列上，否则字面匹配会静默落空）：
  | 本站值 | 第三方可能写成 |
  | --- | --- |
  | 油汀 | 油汀 / 欧式快热炉 / 铝片散热式 / 导热式 |
  | 暖风机 | 暖风机 / 小太阳 / 对流式 / 电暖炉 |
  | 半自动咖啡机 | 意式 / **意大利式** / 半自动 / 全自动 |
  | 嵌入式空调 | 风管机 / 天花机 / 中央空调 / **嵌入式空调** |
  | 台扇/桌面 | 台扇 / 桌面 / 壁扇 / 转页扇 / USB 风扇 |
- 处理方式：**逐字段白名单 + 异常阈值剔除**（例：风暖功率 < 500W 判错标、水箱容量 < 10 判单位错），
  通不过的写 `查不到`，并把剔除理由记进 `change_log`。宁可少一列，不写错一个数。
- 批量归类脚本见 `scripts/classify-facets.py`（规则表）与 `scripts/fetch-evidence-2.py`
  （按白名单补抓分类字段，幂等可重跑）；**没有分类依据的保持「未归类」，不猜**。

## 与并行 Agent 的配合

本仓库可能同时有多个 Agent 在工作：一个负责**采集**（A），一个负责**审核修正**（B）。
**动手之前先读仓库根目录的 `AGENTS.md`**「分区流转协议」——数据按状态放在四个物理分区里，
各方只写自己的分区：

- **采集（A）**：只写 `data/_draft/`，收录完成后 `npm run flow:submit -- <品类>/<id>...` 提交待审。
  发现已入库数据有误 → 复制到草稿区改好再 submit（自动按订正稿处理），**绝不直接改 products.json**。
- **审核修正（B）**：`flow:claim` 认领待入库数据、`flow:recall` 召回已入库数据，在 `data/_review/`
  核验修正，`flow:publish` 入库；不符收录标准的 `flow:return` 退回或（经用户确认）`flow:drop` 剔除。
- **谁都可以**：`npm run flow:status` 看四个区现状，`npm run flow:log` 查流转历史。

每个 flow 命令跑完当场提交（命令不做 git 操作），`data/_flow/journal.jsonl` 是跨 Agent 的共享事实。

## 维护速查

- 加产品：写入 `data/_draft/<品类>/<id>.json`（字段照抄同品类其他产品；`tier` 等分组值必须在 `schema.groupBy.order` 内），然后 `npm run flow:submit -- <品类>/<id>`。
- 订正已入库产品：把该产品从 `products.json` 复制到草稿区改好，`flow:submit` 提交（工具自动识别为订正稿，入库时整条替换）。
- 加字段：在 `schema.json` 的 `fields` 里加一项，指定 `key`/`label`/`type`/`card`/`compare`/`sortable` 等；改前先 `flow:status --category <品类>` 确认该品类没有在修产品。
- 加品类：见上文「数据模型与文件约定」，无需写 Vue 代码。
- 流转命令速记：`flow:status` 看现状；A 用 `submit`/`withdraw`；B 用 `claim`/`recall`/`publish`/`return`/`drop`。
